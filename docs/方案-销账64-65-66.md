### #65 判断说明（2026-11-20 裁决后补充：补附件不改变测试意图）

该用例 `multi_status_filter_matches_any_of_the_statuses` 的**测试意图是「多状态过滤匹配任意状态」**——它 `mk()` 造 3 张凭证后 `update_voucher` 把状态分别置为 draft/reviewed/exported，再断言 `VoucherQuery { statuses: ["draft","exported"] }` 恰好返回第 1、3 张（单值兼容、空数组不筛另有断言）。**它不涉及附件规则断言**（不在任何断言里读 `attachment_required` / 附件路径）。

补附件夹具（`mk()` 造图）的作用只是**让 `update_voucher` 的复核前置条件合法**——B2a 后无图凭证不能再复核，这是 `attachment_required` 的规则，不是本用例要测的语义。补附件后：
- 夹具产生的 3 张凭证各有 1 张合法附件。
- **附件构造来源（已核实）**：`record_attachment_flow.rs` 的 `attach(ctx, voucher_id)`（L16）是**文件级私有函数**（`fn attach`，不在 `tests/common/mod.rs`），且依赖该文件自己的 `attachment_repo::insert` 与 `NewAttachment{...}` 构造——**不可跨文件复用**。因此**改为在 `voucher_link_flow.rs` 内新增最小附件构造逻辑**（同款 `attachment_repo::insert(conn, &NewAttachment{...})` 数行；或抽到 `tests/common/mod.rs` 共享——二选一，推荐抽共享以服务未来其他测试），不引用 `record_attachment_flow.rs`。
- `update_voucher` 复核放行，状态被正确置为 draft/reviewed/exported；
- 后续全部断言集中在 `VoucherQuery.statuses` 过滤行为上，**仍测多状态过滤，不含附件规则断言**。

若在修改中发现「补附件后断言需读附件字段才能过」——那说明测试意图已被破坏，届时**拆测试**（多状态过滤独立成例；附件/复核规则另立用例），并记录拆因。按当前实现判断该情况不会发生（复核只要求附件存在，不进入断言面）。
