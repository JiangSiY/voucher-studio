# 项目代码审计指南（voucher-studio）

> **定位**：本文件是**规范类活文档**——审计怎么查、查到什么算几级、什么算闭环，都以此为准；随仓库演进更新。
> **与其它文档的分工**：本指南 = 方法与口径；`docs/voucher-studio-audit-YYYY-MM-DD.md` = **时点快照**（该次审计的结论，正文冻结、只加头部校正注记）；
> 审计发现的待办 = `docs/开发日志.md` 文末「当前挂账」表（条目制）；**可复现的模式 = 守卫/门禁**（代码资产，不是文档）。
>
> **本仓的核心经验**：靠约定不如靠门禁。审计每发现一个"会再犯"的模式，都要问一句"能不能做成守卫"——能就做成守卫（见 §5）。
> 历史审计：`voucher-studio-health-check-2026-09`（体检）· `-project-analysis-2026-09-09`（综合分析）· `-fix-status-vs-analysis-2026-09-09`（修复对照）· `-status-audit-2026-09-17`（现状审计）。

## 1. 审计范围（15 个维度）

每次全量审计按本表逐面过一遍；**「自动化程度」列决定是人工查还是跑脚本**（§3 的 `scripts/audit.sh` 覆盖"自动"档）。

| # | 维度 | 查什么 | 自动化程度 |
|---|---|---|---|
| 1 | **架构与分层** | 命令层是否直连 `db::repos` / 裸连接；`voucher-core` 是否零 Tauri 依赖；跨层调用方向 | ✅ CI grep 门禁 |
| 2 | **错误处理与契约** | `CoreError` 变体是否覆盖新错误；`ApiError{code,message}` 是否一致；错误文案能否定位（含路径/标识） | 半自动（文案抽查） |
| 3 | **数据一致性** | 事务边界（IO 是否在事务内）；单一真源（配置/口径）；**计数 ↔ 列表口径是否等价**；并发不变量 | 半自动（计数对比靠用例） |
| 4 | **安全** | SQL 参数化与 `LIKE` 转义；路径穿越 / zip-slip / 盘符与 UNC；凭据是否只走 keyring；传输 https 与回环判定；`unsafe` 逐处 | 半自动（模式扫描） |
| 5 | **备份与恢复** | 原子性（fsync + rename）；加密（AEAD 信封）；回收 fail-closed；大文件流式 | 半自动 |
| 6 | **并发与锁** | 锁中毒恢复；重入死锁；**持锁期间是否做重活**（推理/IO/网络） | 半自动（结构式守卫） |
| 7 | **性能** | 主线程阻塞（重活是否 `spawn_blocking`）；全表扫/全量拉取；分页与渲染上限；内存峰值 | 人工（需压测） |
| 8 | **前端健壮性** | 请求竞态（乱序响应）；监听/定时器泄漏；静默吞错（`catch {}`）；单一数据流 | 半自动（模式扫描 + 用例） |
| 9 | **契约与守卫** | invoke 名一致性；配置默认值双端对齐；令牌/附件路径/下钻参数/控件尺寸/IA 三处登记 | ✅ 契约测试 |
| 10 | **测试有效性** | 「假绿」（静默 skip）；覆盖空白；**用例数三处口径一致** | ✅ 脚本核对 |
| 11 | **平台与打包** | 仅 macOS 的既定口径；CI 三 job；产物自包含与部署目标；签名/公证状态 | ✅ CI + 打包自检 |
| 12 | **文档与代码一致性** | 四类文档（规范类/快照/日志/清单）是否同步；**注释时效**（"待补/下一步"是否已过期） | 半自动（关键词扫描） |
| 13 | **无障碍 a11y** | 键盘可达（全流程无鼠标）；焦点管理（陷阱/归还/可见）；`aria-*` 与 `role`；对比度；`prefers-reduced-*` 三档；**放大字号下不溢出** | 人工（清单见 §4.3） |
| 14 | **供应链** | 依赖 pin 策略与理由；锁文件同步；漏洞扫描与许可审查的**有无** | 半自动（现状盘点） |
| 15 | **可观测性** | 日志分级与落盘；错误是否可诊断；崩溃恢复报告；长任务进度可见性；**静默失败是否有痕迹** | 人工 |

## 2. 严重度分级（四档，定义唯一）

| 级别 | 定义 | 典型例子 | 处置 |
|---|---|---|---|
| **P0** | 安全 / **数据损坏**：可能丢数据、写坏数据、越权、凭据泄漏 | 路径穿越未被拒；事务外写库导致半截数据 | **立即修**，修不完不发版 |
| **P1** | **发布门**：用户可见的功能错误、**口径不一致**、契约破坏、门禁缺失 | 待办计数与点进去的列表不一致；某命令未进守卫 | **本轮修完**（用户已定） |
| **P2** | 技术债：可维护性、缺守卫、性能隐患 | 静默 clamp；缺交叉用例；模式扫描命中但无害 | 进挂账表 |
| **P3** | 卫生：命名、注释、文档漂移、格式 | 过期注释；清单计数不同步 | 进挂账或顺手修 |

**判定要求**：级别必须能一句话说清"为什么是这一档"，并在报告的「影响」列写清用户/数据后果（不写"建议优化"这类无后果描述）。

## 3. 执行方式

### 3.1 自动部分：`bash scripts/audit.sh`

一条命令跑出分节摘要（`[OK] / [WARN] / [FAIL]` + 计数）；`--strict` 时出现 FAIL 退出码非 0（可用于后续接 CI）。
脚本**只做"能自动且稳定"的检查**：门禁复用、用例数三处口径、危险模式计数、契约守卫存在性、文档纪律抽查、打包自检抽查。
**脚本查不出的（判断类）必须人工**：口径是否**语义等价**、a11y 实感、依赖策略是否合理、性能是否够用。

### 3.2 人工部分（每面给证据，不给印象）

- **必读代码**：本轮 `git log <base>..HEAD` 涉及的新增/大改文件（先读"承担什么职责"，再读实现）
- **必须交叉验证的口径**：凡界面上"计数/汇总"与"点进去的列表"来自**两条不同 SQL** 的，都要用例或手工核对（这是本仓历史上真实出过的一类问题）
- **必须逐处看的**：`unsafe`、生产 `unwrap/expect`、事务内的 IO、动态 SQL 拼接、静默 `catch {}` 与 `unwrap_or_default`

### 3.3 取证纪律

- 每条发现必须有 **`file:line` 或命令输出**作为证据；无法取证的不写进报告（可写"未能取证，需人工"）
- **不在审计中顺手大改**：P0/P1 按 §2 处置；P2/P3 只登记（避免"边审边重构"导致审计结论失真）
- 审计本身**要过门禁**：修完 P0/P1 后，四门 + 三门 + 两道 grep 守卫必须全绿

## 4. 发现字段与闭环判据

### 4.1 字段（固定，缺项写"—"）

`编号 / 维度 / 严重度 / 现象 / 证据 / 影响 / 建议 / 验收标准 / 状态`

### 4.2 **闭环三档**（本指南的关键新增，解决历史"改完即闭环"的虚假收口）

| 档 | 含义 | 要求 |
|---|---|---|
| **L1 代码已改** | 改了代码 | 附提交 sha |
| **L2 有权锁定** | 有守卫/用例防止回退 | 附测试名；**可复现的模式必须到这一档** |
| **L3 真机复验** | 在真实环境确认过 | 附证据路径（截图/日志/走查记录） |

**未达 L3 的一律进挂账「验证缺口」条目**（本仓既有实践：挂账 #24/#25/#26 就是这类）。反之，只有 L1 而没 L2 的，报告里必须写"未固化，可能回退"。

### 4.3 a11y 人工清单（首次纳入，逐条实测）

1. 全流程键盘可达：Tab 顺序合理、无"只能点"的关键动作（保存/翻张/处置/导出）
2. 焦点：对话框与命令面板打开时**焦点进入并被困在内部**、Esc 关闭后**焦点归还触发元素**、`:focus-visible` 清晰可见
3. `aria`：交互控件有可读名称；图表有 `role="img"` + 概述；`aria-live` 用于异步结果
4. 系统偏好三档：`prefers-reduced-transparency`（材质回退实色）、`-motion`（动效关闭）、`contrast`（分隔线与文字加强）
5. **放大字号承受力**：界面字号切「更大」后逐页看**无截断、无横向溢出、无文字重叠**（本项目默认即偏大，见设计正本 §0.6）

## 5. 报告、挂账与守卫化

| 环节 | 做法 |
|---|---|
| 报告存放 | `docs/voucher-studio-audit-YYYY-MM-DD.md`（**日期粒度统一**；`health-check` 曾用月份，属历史命名） |
| 报告性质 | **时点快照**：正文永不修改；需更新只在**头部**加校正注记并指向当前真源（`AGENTS.md` 文档纪律） |
| 待办跟踪 | `docs/开发日志.md` 文末「当前挂账」表：一条一个编号，`来源` 列回指审计编号，`状态` 列用 ⏳/✅/作废 |
| 强制日志 | 审计属"必须追加开发日志条目"的时机之一（7 字段，含门禁证据） |
| **守卫化** | 能自动化的模式 → 契约测试或 CI grep 门禁；无法自动化的 → a11y/走查清单（§4.3）与真机验收（`docs/验收基线/清单2/3`） |
| 清单增补 | 新的人工验收项写入清单2/3：**只增不删、编号不重排**（作废项标"作废"不删行） |
