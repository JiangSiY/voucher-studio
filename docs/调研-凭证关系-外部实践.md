# 凭证「关联关系」建模调研报告

> 面向对象：一个自用桌面工具，当前模型是「1 张图片 = 1 张凭证」（日期 / 金额 / 对方 / 摘要 / 备注 / 标签），没有凭证之间的关系概念。
> 本文回答：主流财务软件与文档管理系统如何建模这种关系、有哪些会计口径风险、六个候选建模方案各自的取舍、以及交互与输出该怎么呈现。

---

## 摘要（先看这 8 条）

1. 所有成熟系统都把「关系」当成**独立的一等公民**，而不是塞进标签或备注：QuickBooks 用事务对象上的 `LinkedTxn[]`，NetSuite 用行级多对多表 `Transaction_links`，金蝶云星空用 `T_BOTP_LINKTABLE` + 分录表，Sage 用独立资源 `Allocations`。
2. 但「关系」在会计里**不是一个概念，至少是四个**：① 血缘（谁生成了谁，有方向）、② 核销/分摊（带金额、有余额约束）、③ 说明/佐证（无金额、纯语义）、④ 装箱（组/批次/一张凭证带一堆附件）。混在一个字段里必然出错。
3. **「带金额的关联」和「不帶金額的關聯」必须分开建**。Sage 的分配带 `Amount` 且强制「不得超过源付款的未分配余额」；QuickBooks 的 `LinkedTxn` 只带 `{TxnId, TxnType}` 不带金额。
4. 会计口径上最重要的一条原则是**关联 ≠ 抵消**：IAS 1.32 明确「除非准则要求或允许，企业不得将资产与负债、收益与费用相互抵消」([ifrs.org](https://www.ifrs.org/content/dam/ifrs/meetings/2015/november/ifrs-ic/ias-32-financial-instruments/ap10-offsetting-in-respect-of-certain-cash-poolin.pdf))。把两张凭证「关联」后，合计口径必须保持「分别列示」。
5. 中文会计实务里早就有现成的答案：**记账凭证是主件、原始凭证是附件**，凭证上必须标注「所附原始凭证的张数」；一张原始凭证涉及多张记账凭证时，**附在一张主要的记账凭证后面，在其他记账凭证上注明该凭证的编号**（《会计基础工作规范》第五十一条）([jdy.com](https://www.jdy.com/news/1110045934.html))。这几乎就是「主凭证 + 子凭证 + 反向指针」的手工版。
6. 文档管理软件的经验反过来证明：**纯标签方案会崩**。Paperless-ngx 的官方关联需求帖里有人攒了 **448 个标签**只为了把同一批单据粘起来，还有人把主文档的 md5 写进备注当组 ID ([discussion #2007](https://github.com/paperless-ngx/paperless-ngx/discussions/2007))。Paperless 官方文档也明确把标签定位成「more versatile folders or binders」([docs](https://github.com/paperless-ngx/paperless-ngx/blob/main/docs/usage.md))——它能解决「归堆」，解决不了「谁解释谁」。
7. 工程上最容易踩的坑不是建模，而是**断链**：金蝶明确写了「下推后不保存直接关掉会留下**悬空关联**」「清理悬空关联是上线后必做的数据治理动作」，以及「Excel 导入的单据不带关联关系，这是最常见的断链来源」([club.kdcloud.com](https://club.kdcloud.com/article/886252982046442240?productLineId=0&lang=zh-CN))。用友也暴露过同样的问题：申请单上的附件在付款单里看不到、多张生产加工单关联同一张材料出库单时表头显示不全 ([chanjet.com](https://www.chanjet.com/sem/wchatask/qa-73477.html))。
8. **打印侧是全行业的共同短板**：NetSuite 想把 related records（已核销的付款/贷记单列表）打进 Advanced PDF 模版，唯一回答是「我还没见过能做到的办法，我认为做不到」([stackoverflow](https://stackoverflow.com/questions/46306951/in-netsuite-how-do-i-print-related-records-in-advanced-pdf-html-template))。中文实务反而给了可操作的答案：附件粘贴单上要**分类列出每类原始凭证的张数、单价与总金额**，并单独计附件张数 ([dongao.com](https://www.dongao.com/cjks/jjfjc/201909261161916.shtml))。

## 1. 主流工具怎么建模这种关系

### 1.1 横向对比（先给结论表）

| 系统 | 关系载体 | 是否带金额 | 方向性 | 关系类型 | 附件位置 |
|---|---|---|---|---|---|
| QuickBooks Online | 事务对象上的 `LinkedTxn[] {TxnId, TxnType}` | 否 | 双向可查，但按类型分读写权限 | 由 TxnType 隐含（Estimate / Payment / ReimburseCharge…） | 独立实体 `Attachable`，通过 `AttachableRef[].EntityRef` 指向事务 |
| Xero | 没有通用链接实体；靠 Allocation（贷记单/预付/多付/付款 applied 到发票） | 是（付款金额） | 付款→发票 | `CreditNotes` / `Prepayments` / `Overpayments` 分类字段 | 附件挂在父对象 URL 下（`Invoice/{Guid}/Attachments/`） |
| Sage | 独立资源 `Allocations` | 是（`Amount`） | 有明确 source/target | source=付款，target=贸易单据 | 未见独立文档链接，靠分配 |
| NetSuite | 行级多对多表 `Transaction_links` + UI 链接 | 是（`amount_linked` / `quantity_linked`） | `original_*` → `applied_*` | `link_type` / `link_type_code` | 事务自身字段与子标签；自定义记录可用「Record is Parent」做 child |
| 用友（好会计/好业财/NCC） | 单据「关联单据 / 联查」+ 凭证上的「附单据数」 | 否（关联本身） | 主单→子单 | 由单据类型决定（销货单→收款单/出库单） | 附件挂在**源头单据**上（付款单看不到申请单的附件） |
| 金蝶云星空 | `T_BOTP_LINKTABLE`（关联关系表）+ `T_BOTP_LINKTABLEENTRY`（分录级关联与数量） | 是（关联数量，用于控制下推） | 源单→目标单，可上查下查 | 由转换规则定义 | 单据附件；总账凭证有「附件数」字段 |
| 易快报（费控） | 报销单/借款单上的「申请单」字段 + 「核销借款」 | 核销带金额 | 报销单→借款单/申请单 | 关联申请单、核销借款 | 附件在单据上 |
| Paperless-ngx | **无原生文档间关联**；用标签/自定义字段近似 | 否 | 无 | 无 | 文档本体即附件 |
| Mayan EDMS | Smart Links（按元数据规则自动匹配） | 否 | 单向（规则） | 规则条件表达式 | 文档版本 |
| DEVONthink | Item Links / WikiLinks（正文内引用） | 否 | 正文指向目标，但系统统计双向数量 | 无（链接本身无类型，靠正文措辞） | 文档本体 + Annotation |

### 1.2 QuickBooks Online：关系在事务对象上，附件是独立实体

- **关系**：Invoice / Bill 等事务对象上有一个 `LinkedTxn [0..n]` 数组，元素只有 `{TxnId, TxnType}`；要拿详情得用 `TxnId` 再发一次读请求。支持的类型里，`Estimate`、`TimeActivity` 可以通过 API 建链（一个 Invoice 只能链一个 Estimate，Progress Invoicing 不支持 API）；而 `Payment` 以及 `ReimburseCharge / ChargeCredit / StatementCharge`（对应 billable 的 Cash / Delayed Credit / Delayed Charge）**只能在 UI 建链、API 只读**。删除时原文要求：`You must unlink any linked transactions associated with the invoice object before deleting it`——**删除前必须先解除关联**，这是很值得抄的完整性约束。([developer.intuit.com](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/invoice))
- **表级视角**（第三方驱动暴露的结构）：`InvoiceLinkedTransactions` / `BillLinkedTransactions`，列有 `LinkedTxnId [KEY]`、`BillId [KEY]`（外键指向 Bills.Id）、`SyncToken`、`DocNumber`、`TxnDate`、`MetaData_CreateTime / LastUpdatedTime`。官方描述是「Tracks relationships between vendor bills and linked transactions, such as purchase orders or payments」([CData: BillLinkedTransactions](https://cdn.cdata.com/help/RNM/ado/pg_table-billlinkedtransactions.htm)、[InvoiceLinkedTransactions](https://cdn.cdata.com/help/RNM/mcp/pg_table-invoicelinkedtransactions.htm))。
  - **注意**：它把「付款↔账单」和「采购订单↔账单」放在同一张 LinkedTransactions 表里，靠 `TxnType` 区分——这印证了「一个关联表 + 类型字段」是能落地的。
- **附件**：QBO 的附件是独立实体 `Attachable`，不是事务上的字段。关键属性：
  - `AttachableRef[]`，其中 `EntityRef {type:"Invoice", value:"95"}` 指定归属事务（是**数组**，可指向事务或 Item）；
  - `IncludeOnSend`（是否随发票邮件一起发给对方）——这是「打印/对外输出」行为挂在附件上的例子；
  - `Note`（可以单独存在，即**纯文字条目本身就是一个实体**）、`FileName`、`Category`（Contact Photo / Document / Image / Receipt / Signature / Sound / Other）([developer.intuit.com](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/attachable))。
  - 对本文档工具的直接启发：QBO 把「附注/说明」和「文件」统一成一种可被关联的实体——这正是方案 F（虚拟凭证/纯文字说明条目）的商业级先例。
- **界面呈现**：`Invoices and Received Payments` 报表按客户分组，Payment 行加粗、其关联的发票列在下面（「one payment that covers two invoices」），点 Payment 打开后反过来显示它挂的两张发票——**双向可下钻**([gentlefrog.com](https://gentlefrog.com/how-to-find-payments-linked-to-invoices-quickbooks-online/))。官方的 Linked Transactions report 帮助页存在但本次抓取被 403 拦下，未能读正文：[quickbooks.intuit.com](https://quickbooks.intuit.com/learn-support/en-us/help-article/report-management/run-linked-transactions-report-quickbooks-online/L1qhOwaFj_US_en_US)。

### 1.3 Xero：没有「文档链接」，只有「核销」

- Xero 的 API 里**找不到通用的文档间关联实体**。它的关系全部通过核销表达：Invoice 对象上返回 `CreditNotes`（已核销到该发票的贷记单）、`Prepayments`、`Overpayments`，以及一个汇总字段 `AmountCredited`＝「Sum of all credit notes, over-payments and pre-payments applied to invoice」；付款则要通过 payments 端点 applied 上去([developer.xero.com/invoices](https://developer.xero.com/documentation/api/accounting/invoices/)、[creditnotes](https://developer.xero.com/documentation/api/accounting/creditnotes))。
- **附件同样是「挂在一个父对象上」**：`{Endpoint}/{Guid}/Attachments/{Filename}`，Guid 就是父对象（如 ReceiptID / InvoiceID）。一个附件只属于一个父对象，因此**不产生任何文档间关系**([developer.xero.com/attachments](https://developer.xero.com/documentation/api/accounting/attachments))。
- **界面侧的合单/拆单**发生在 Reconcile 的 `Match` / `Find & Match`：一笔银行收付款可以勾选多张 invoice/bill，金额对平后银行交易变绿；金额有零星差异时用 minor adjustment，差额自动进 Rounding account([mdp.co.nz](https://www.mdp.co.nz/resources-and-news/xero-tip-allocation-of-payments/)、[central.xero.com](https://central.xero.com/0/article/Reconcile-a-bank-statement-line-using-Find-Match)、[Pay multiple bills](https://central.xero.com/s/article/Pay-multiple-bills-AU))。
- **审计轨迹是内建的**：每一张 invoice / bill / transaction 页面底部都有 `History & Notes`，可以看「谁在什么时候改了什么」，官方定位是 built-in audit trail([afsl.nz](https://www.afsl.nz/xero-tip-of-the-month-accessing-the-history-and-notes-feature))。

### 1.4 Sage：把「关联」做成带金额、有余额约束的独立资源

- Sage 有独立的 `Allocations` 资源，官方描述是「allocation links between existing payment transactions and trade documents」；DELETE 的语义写作「removing the bookkeeping link between the source transaction and the target transaction」。
- 建链结构是 `Items[]`，每项只有三个字段：`SourceTransactionId`（付款类事务，如 customer receipt）、`TargetTransactionId`（贸易单据，如 sales invoice）、`Amount`；一次最多 5 项；分配日期强制取 source 的 `Date`。
- **最关键的一条不变量**：`Amount` 「must be greater than zero and **must not exceed the unallocated balance of the source payment**」——即一笔付款被分摊的总额不能超过它自身金额，从数据结构上消灭了「重复计入合计」([developer.sage.com](https://developer.sage.com/embedded-accounting/apis/embedded-accounting/latest/openapi/groups/transactions/tags/allocations.md))。
- 表级结构可参考 [Sage 200 Database PDF](https://desktophelp.sage.co.uk/sage200/PDF/2015/Understanding%20the%20Sage%20200%202015%20Database.pdf)。

### 1.5 NetSuite：三种链接语义 + 行级关联表

- 官方帮助 `Using Transaction Links` 把链接明确分成三类（这段几乎是本文档工具的需求说明书）：
  1. **Created From**（上游）：如 sales order 上打开生成它的 estimate；
  2. **下游**：如 estimate 上的 `Orders and Sales` 链接打开由它生成的 SO / cash sale / invoice；
  3. **applied to**（核销）：payment / credit 链到被核销事务，呈现在 subtab 上，如 deposit 页的 `Payments` 子标签([NetSuite 帮助镜像](https://netsuitedocumentation1.gitlab.io/netsuitedocumentation1/section_N551392.html)、[docs.oracle.com](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_N551392.html))。
- **底层表是全行业最彻底的实现**：`Transaction_links` 的复合主键是 `(original_transaction_id, original_transaction_line_id, applied_transaction_id, applied_transaction_line_id, link_type_code, inventory_number)`；列包含 `link_type` / `link_type_code`（关系类型）、`amount_linked`、`amount_foreign_linked`、`quantity_linked`（金额/数量）、`applied_date_posted`、`original_date_posted`（时间）、`date_last_modified`；外键同时指向 `Transaction_lines` 与 `Transactions`([netsuite.com](https://www.netsuite.com/help/helpcenter/en_US/srbrowser/Browser2021_2/odbc/record/transaction_links.html))。
- Transactions 表里还有几个**冗余的方向字段**：`created_from_id`（Created from ID）、`related_tranid`（Related transaction ID）、`is_created_from_merge`（是否由合并生成）([transaction.html](https://www.netsuite.com/help/helpcenter/en_US/srbrowser/Browser2021_2/odbc/record/transaction.html))。也就是说：**既有关联表（权威），又在主表上留了冗余指针（便于查询）**。
- **粒度之痛**：链接做在**行级**而不是整单上，所以用 ODBC 想还原 UI 上那个「Created From」很难——社区原话是「the links are done on each line versus the whole transactions like in a saved search」，只能靠「unique links = 1」之类去推断([netsuitehub.com](https://netsuitehub.com/forums/topic/created-from-in-transaction-search/))。**教训：如果不需要按行分摊，就不要下沉到行级。**
- **方向命名的实战灾难**：「Applied To」和「Applying Transaction」是两个反向 join。以 Type=Invoice 为例，`Applied To Transactions` 指在事务流中**先于**发票、造成该发票的记录（Sales Order / Opportunity / Estimate / Credit Card / Bill / Bill Credit / Expense Report，含标记 billable 的应付类）；`Applying Transaction` 指**后于**发票、被核销上去的记录（Payment / Return Authorization / Deposit Application / Journal / Credit Memo / Item Receipt / Currency Revaluation）([plative.com](https://plative.com/insights/blog/the-netsuite-eternal-conflict-applied-to-vs-applying-transaction/))。**教训：UI 上永远不要用「applied」这种双向词，要么写「上游来源」，要么写「已核销到」，且两个方向各给一个区块。**
- **子记录模式**：在自定义记录上放一个 `Type=List/Record, List/Record=Transaction` 的字段，勾选 **"Record is Parent"**，再建 Subtabs 挂到事务记录上，用户就能从父事务直接访问子记录([technologyblog.rsmus.com](https://technologyblog.rsmus.com/technologies/netsuite/automating-child-record-creation-with-custom-records-and-workflows-in-netsuite/))。这就是方案 C（自引用父子树）的商业实现方式，而且它选择「用侧栏 subtab 呈现」而不是「把子记录平铺进列表」。
- **打印相关记录是公认做不到的事**：见摘要第 8 条与 [stackoverflow #46306951](https://stackoverflow.com/questions/46306951/in-netsuite-how-do-i-print-related-records-in-advanced-pdf-html-template)。

### 1.6 中文记账软件：凭证附件数、附单据数、联查、核销

**金蝶云星空（单据转换/下推 + 关联关系表）**——对建模最有参考价值的一篇：
- 核心表：`T_META_CONVERTRULE`（转换规则主表）、`T_META_CONVERTRULEENTRY`（转换规则分录/字段映射）、**`T_BOTP_LINKTABLE`（关联关系表，下推登记，上查下查依据）**、**`T_BOTP_LINKTABLEENTRY`（关联关系分录，分录级关联与数量）**([club.kdcloud.com](https://club.kdcloud.com/article/886252982046442240?productLineId=0&lang=zh-CN))。
- 三条核心认知（原文）：**「下推不是复制，是'按规则生成+登记关联'」**（目标单字段由映射规则算出，同时在关联表登记「这张目标单来自哪张源单的哪行」）；**「关联数量是控制下推超量的钥匙」**；「规则属于元数据，随包迁移」。
- **悬空关联**：关联关系是在**下推时**登记而不是保存目标单时，所以「下推后不保存直接关掉」会留下源单显示已下推、目标单却不存在的悬空关联——原文明确「清理悬空关联是上线后必做的数据治理动作」。
- **数量控制**三档：不控制 / 按数量（累计下推数量 ≤ 源单数量）/ 按比例（允许超欠比），公式为 `源单行可下推数量 = 源单数量 × (1 + 允许超欠比) − 已下推累计数量`。
- **反写**（下游审核后回写上游的入库数量/状态）：在目标单操作上配反写规则 → 指定反写字段 → 设触发条件。**反写不生效的排查链**：规则挂在操作上（不是表单上）→ 操作确实执行了 → 关联关系存在（没有关联关系反写找不到源单）→ 反写字段类型匹配。
- **断链四类原因**：下推了但上查看不到（关联登记后未保存/规则被禁用）；上查能看到、下查看不到（单向登记或权限过滤）；关联关系丢失（目标单被删除/反审核后重建）；手工单查不到上下游（**无关联关系属正常现象**）。原文点出最现实的来源：「Excel 导入的单据不带关联关系，这是最常见的'断链'来源」。
- **合并/拆分下推**：合并（多源单→一张目标单）靠**分组策略**按供应商/组织/日期，分组字段选错会把不该合的合到一起；拆分（一源单→多张目标单）靠数量控制，不需要写插件。

**金蝶总账凭证**：凭证录入界面有 **`附件数`** 字段（官方说明：设置凭证录入后以附件的形式备份原始单据的数量）；系统参数「**保存检查附件数**」勾选后附件数为空则不予保存；凭证查询支持「整理、**冲销**、**联查单据和业务凭证**」；还有一条针对银行分录的查重校验：「银行存款科目分录的结算方式和结算号是否重复，如果重复，不予以保存」([help.open.kingdee.com](https://help.open.kingdee.com/dokuwiki_std/doku.php?id=%E5%87%AD%E8%AF%81%E5%BD%95%E5%85%A5))。

**用友（好会计/好业财）**——两个计数器要分开，这一点特别值得抄：
- 凭证界面把「**附件数**」和「**附单据数**」**分开显示**；「附单据数」取决于凭证来源——多条日记账/多条发票/多条单据合并生成一张凭证时，点【总账】-【查看凭证】的附单据数可以**下钻查到每笔单据的明细**；手工录入的凭证就没有附单据数([chanjet.net](http://chanjet.net/news.asp?id=20303)、[好会计更新](http://23001.cn/news.asp?id=11446)、[凭证能否上传附件](http://chanjet.net/news.asp?id=18731))。
- 也就是说：**「挂上来的文件数」和「合并进来的源单据数」是两个不同的量**，混成一个数字就会算错张数。
- **断链的典型症状**：好业财业务申请付款上传了附件，**付款单中看不到附件**，必须回到对应的付款申请单里看（原文「附件是保存在付款申请单中的，付款单默认不同步显示」）；多张生产加工单关联同一张材料出库单时，**表头不会显示全部来源单据号**，只能在明细里看到（「没有一张报表可以直接显示全部数据」）。
- **主单/子单联查交互**（用友 NCC「离职主单联查」）：主单上有【联查】按钮，点开后**所有下游子单以列表形式展示**，点列窗体号跳转到卡片子单页面，还能从主单侧对子单执行「终止」([developer.yonyou.com](https://developer.yonyou.com/cloud/integrationAsset/assetDetail/1737285921237819394))。
- U8 里「采购发票联查采购入库单时提示『没有相关联的单据』」是同一个病：**联查依赖关联记录存在，历史数据/导入数据天然缺链**([chanjet.net](http://chanjet.net/m/news.asp?id=4527))。

**易快报（费控 SaaS）——借款/报销的核销语义写得最清楚**：
- 「报销、借款关联」：提交报销单或借款单时，可以在「申请单」字段选择要关联的申请单，「让报销/借款有据可依」；审批人审批时**可点击查看所关联申请单的详情**([ekuaibao.com](https://www.ekuaibao.com/help/ekuaibao1/chapter7/section7-4.html))。
- 「借款冲销」：借款成功后可用报销单冲销；提交报销单时点「核销借款」，选择需要冲销的借款单。**一个报销单可核销一笔或多笔已完成的借款单**；**报销金额 > 借款金额时，收到的报销金额为差额；报销金额 ≤ 借款金额时，报销金额直接冲抵**([ekuaibao.com](https://www.ekuaibao.com/help/ekuaibao1/chapter6/section6-2.html))。
  → 这两条合起来就是方案 A 的完整雏形：一个**无金额的语义关联**（申请单，供审批溯源）+ 一个**带金额的核销**（借款冲销，产生差额/冲抵），且核销会改变实际支付金额。

**费控侧的重复报销防控（关系到第 3 节）**：
- 合思「全局去重引擎」：把发票号、金额（精确到分）、开票日期、销售方名称、购买方名称、商品明细等做哈希组合成**多维度唯一性指纹**（避免仅凭发票号去重的漏洞）；跨会计期间、跨法人实体的历史数据统一入池；对篡改字段用 Levenshtein / Jaccard 模糊匹配，相似度超阈值（默认 98%）告警；并支持「同一笔交易不允许拆分报销」这类动态规则([hosecloud.com](https://www.hosecloud.com/blog/651957.html))。
- 泛微·齐业成：把「验真、查重、业务关联」讲成三道防线——**验真是确认发票真伪、查重是确认是否已经报过，两者是两回事**([weaver.com.cn](https://www.weaver.com.cn/subpage/aboutus/news/news-detail.html?id=29576))。

**随手记（个人记账，方案 B/E 的极简先例）**：有独立的「报销中心」，先「创建报销项目名称」，再把公务支出记到该项目下；「财务报销」时金额会自动计算为**该项目下所有公务支出的总和**（也可自定义），并选择收款账户([yesky](https://mydown.yesky.com/news/87376589.html))。**注意：它把「组」和「金额汇总」直接绑定了**——这正是第 3 节要警惕的那种设计（组的合计被当成了事实金额）。

### 1.7 从以上归纳出的 5 个原语

任何方案本质上都是在组合这五种原语，建议在设计时先把它们分开命名，再决定哪几种进你的工具：

| 原语 | 含义 | 是否带金额 | 典型实现 |
|---|---|---|---|
| Link（关联/佐证） | 「这张解释了那张」，纯语义 | 否 | QBO `LinkedTxn`、DEVONthink Item Link、易快报「申请单」 |
| Allocation（核销/分摊） | 一笔钱被分到几处，或不完全对平 | 是，且有余额约束 | Sage `Allocations`、Xero applied、易快报「核销借款」 |
| Heredity（血缘/来源） | 谁生成了谁，有方向 | 否（数量另存） | NetSuite Created From、金蝶 `T_BOTP_LINKTABLE` |
| Container（组/批次/凭证） | 一组凭证归堆，组有标题 | 组本身无金额（合计是派生值） | 随手记报销项目、金蝶合并下推、记账凭证+附件 |
| Attachment（文件挂载） | 文件贴在某条记录上 | 否 | QBO `Attachable`、Xero Attachments、凭证「附件数」 |

## 2. 文档管理类工具怎么做文档关联 / 分组 / 合集

### 2.1 Paperless-ngx：需求最强、原生最弱，社区工作区被"标签洪水"淹没

- **原生没有任何文档间关联**。官方文档把组织维度定义为 tag / correspondent / document type / storage path / custom field /（v2.19 起的）nested tags。它对标签的定位写得很直白：「Think of tags as more versatile folders or binders」——「a single document can have multiple tags. A physical document cannot magically appear in two different folders, but with tags, this is entirely possible」；并建议用 **saved views 当桌上的实体活页夹**（「equal to having labeled physical binders on your desk, except that these saved views are dynamic」）([docs/usage.md](https://github.com/paperless-ngx/paperless-ngx/blob/main/docs/usage.md))。
- **关联需求帖 #2007「Idea: Document linking and referencing」是被官方锁定的长篇讨论**，里面有大量和你完全同构的用例：保险理赔单↔相关发票、终止确认书↔原始合同、医疗收据↔报销对账单、**付款凭证↔发票**、行程单+酒店确认+机票+签证、一次邮件收到的多份文档不想合并只想关联([discussion #2007](https://github.com/paperless-ngx/paperless-ngx/discussions/2007))。
- 该帖里最有价值的三件事：
  1. **反面教材（标签洪水）**：有人用 448 个标签，大多是 `EOBxxxx` 这种「借外部系统的 id 把文档粘起来」的标签；另一人把主文档的 md5 写进所有成员的 comment 字段当组 ID。原文自评「I would not call this 'linking' but grouping」——即**靠值相等的伪关联**能凑出"组"，但做不到"谁解释谁"，且不可发现、不可反向查询。
  2. **作者给 UI 提案（与第 5 节几乎一致）**：编辑页加一个 `Referenced documents` 页签，里面是一个可删除的链接列表，显示**标题 + 日期 + 预览按钮**，点名字跳到目标文档；文档列表页在有链接时显示一个 link 按钮，点开同一个列表弹窗([discussion #2007](https://github.com/paperless-ngx/paperless-ngx/discussions/2007))。
  3. **一条关键需求**：列表里每条链接要有一列**自由文本说明**，用来写「以什么方式关联」，原文举例 `Related insurance:`——即**关系类型/说明必须是用户可写的文本，而不只是枚举**。
- 替代路径：**自定义字段**（讨论 #141「Custom metadata for documents」被合并为实现 PR #4502）现在让用户能把共享的组 ID 写进结构化字段；它能替代一部分脏标签，但仍然需要「先自己知道那个 ID」([discussion #141](https://github.com/paperless-ngx/paperless-ngx/discussions/141))。nested tags（v2.19，最深 5 层、加子标签自动加父标签）解决了标签的层级整理，但**不解决文档之间的关系**([docs/usage.md](https://github.com/paperless-ngx/paperless-ngx/blob/main/docs/usage.md))。
- 另外 Paperless 详情页已有 `document history`（操作历史），这是第 3 节「审计轨迹」的轻量参考。

### 2.2 Papermerge：文件系统式文件夹 + 版本 + 页管理 + 合并

- 模型是**文件夹层级**（"Folder ... counterpart of 'folder' concept used in major operating systems"）+ 文档类型/分类 + 标签 + **文档版本**（原始版本为 version 1）+ **页面管理** + **合并文档**（merge documents）([docs.papermerge.io 概念](https://docs.papermerge.io/3.5/user/getting-started/)、[document types](https://docs.papermerge.io/3.5/user/document-types/)、[folders](http://docs.papermerge.com/organizing/folders/))。
- 它的答案是「**别关联，直接合并/移动页**」：把多份扫描件的页面并进一个文档，或用文件夹把同一批放一起。**合并的代价是丢失来源**——合并后你就再也不知道某页原本属于哪张单独凭证了。这正是你方案 D 要考虑的边界。
- 只支持 PDF / TIFF / JPEG / PNG 四种格式。

### 2.3 Mayan EDMS：用"规则"代替"手工链接"，官方自认不够用

- 官方 `smart_links.rst` 定义得很精确：**Indexes 是自动的层级单元（用于归堆），Smart Links 是文档之间的自动引用**——「Smart links are rule based, but **don't create any organizational structure**. Smart links just show the documents that match the rules as evaluated against the metadata or properties of the currently displayed document.」例：`Patient records` 文档上按 `Prescription` 元数据值自动匹配 `Prescription information sheets`([Mayan smart_links.rst](https://gitlab.com/mayan-edms/mayan-edms/-/blob/1ad68a61f565ec0eb1f3d03b14c96c6d0d5349cc/docs/topics/smart_links.rst))。
- **但官方的邮件列表给出了这个设计的失败告终**：有用户要 A/B/C/D 四份方案文档分别引用 1/2/3 号参考文档，穷举后问「有没有简单办法手工链接两份文档」，项目作者 Roberto Rosario 的回答是：需要为每一对关系加不同的 metadata / 文档类型 / 标签等**区分物**，「it is not possible to create a relationship logic if ... all have the same attributes each. **The other solution would be to add support for manually linking documents.**」([mail-archive](https://www.mail-archive.com/mayan-edms@googlegroups.com/msg01517.html))。
- **这是本次调研里最有分量的一条结论**：**用「元数据一致」来推导「文档相关」的自动链接方案，会在关系数上升时把元数据体系撑爆；用户要的是手工链接。** 你的工具请直接给手工链接。

### 2.4 DEVONthink：链接做进正文，但系统维护双向计数与可视标记

- 两种机制：
  - **Item Links**：每份文档/分组/数据库都有唯一 URL（item link），可以贴进任何支持 URL 的地方（甚至 Calendar、Mail），也可以链接到 PDF 里某个具体位置的**深链接**（`Copy Selection Link` / `Copy Annotation Link`：点开直接滚到并选中那段文字）([DEVONthink Linking](https://www.devontechnologies.com/apps/devonthink/linking)、[Take Control of DEVONthink 4](https://download.devontechnologies.com/download/ebooks/TCoDEVONthink4-1.0.pdf))。
  - **WikiLinks**：在富文本里 `.Make Link` 或者自动识别（MashedWords / `[[方括号]]` / 文档全名与别名）建立按名字的链接，「如果这个名字还没有文档，第一次点击时会用模版新建一个」——即**先写链接、后到文档**，正好治「问题文档先到、答案文档后到」这个场景。
- **系统级的关键设计（强烈建议抄）**：
  - 文档列表里，**有出链的显示 outgoing link 图标，有入链的显示 incoming link 图标**；系统在后台计算每份文档的入链/出链数量，并可用于**搜索、智能分组和列表排序**。
  - 改文档名时可以选择自动更新指向它的链接名（`Settings > WikiLinks > Update name of item links automatically`）。
  - **已知坑**：若库里有同名文档，自动 WikiLink「可能选错」，而且**无法强制指定**，只能改用手工 Item Link([Take Control 电子书 p.164–169](https://download.devontechnologies.com/download/ebooks/TCoDEVONthink4-1.0.pdf))。
  - 另有 See Also / 图谱（AI 相似度推荐）作为「自动发现」，与「手工引用」并存——**推荐是发现，不是事实**。

### 2.5 文档管理类的结论：最实用的 5 个交互

1. **详情页一个「相关文档」区块/页签**（Paperless 社区提案、NetSuite subtab、用友联查都指向同一形态），列表显示：标题 / 日期 / 金额 / **关系说明文本** / 预览。
2. **反向可见**：不只在 A 上看到 B，也要在 B 上看到「被 A 引用」（DEVONthink 的 in/out 图标 + QBO 的双向下钻）。
3. **链接可搜索、可筛选、可排序**（DEVONthink 把 in/out 链计数做成可检索字段；否则关联就是死数据）。
4. **组/合集用 saved view / 动态视图呈现**（Paperless 官方建议），而不是把成员硬搬进一个"文件夹"。
5. **关系要有自由文本说明列**（Paperless 讨论里最一致的诉求），否则「说明/佐证/冲销」这三类会被用户写进标题里。

**明确的坑**：把标签当关系（448 标签案例）；把元数据值相等当链接（Mayan 官方结论）；把「合并」当成「关联」的替代（Papermerge 合并后丢失来源）。

## 3. 会计口径上的风险与公认处理原则

### 3.1 风险一：关联被误解为"抵消/合并"

- **公认原则**：IAS 1.32（NIC 1.32）——「An entity shall not offset assets and liabilities or income and expenses, unless required or permitted by an IFRS」([IFRS 基金会会议文件](https://www.ifrs.org/content/dam/ifrs/meetings/2015/november/ifrs-ic/ias-32-financial-instruments/ap10-offsetting-in-respect-of-certain-cash-poolin.pdf)、[IFRS 示例文件中的 NIC 1.32 原文](https://cdn.ifrs.org/-/media/project/primary-financial-statements/exposure-draft/ed-illustrative-examples-sp.pdf))。含义：**把两张凭证"关联"起来，不代表可以把它们净额列示**；只有准则要求或允许时才允许抵消（典型的允许情形是同一对手方、同一到期日、有法定抵消权等）。
- **落到你的工具上**：任意两张凭证建立「说明/佐证」关系后，任何合计、月报、导出都必须**继续分别计入**，不能因为"相关"就抵掉或合并。若真要做抵消（冲销/红冲），必须是一个**独立的关系类型 + 显式的带符号金额**，而不是普通关联的副作用。

### 3.2 风险二：重复计入合计 / 一票多报

- **公认做法**：以「多维度唯一性指纹 + 全局台账 + 入口即拦截」防重复。合思的做法是发票号+金额（到分）+开票日期+销售方+购买方+商品明细做**哈希指纹**，并把含已作废、已红冲发票的历史数据统一入池、跨期跨组织比对；只用发票号去重是不够的([hosecloud.com](https://www.hosecloud.com/blog/651957.html))。
- **另一条独立原则**：**「验真」和「查重」是两回事**（前者证明真伪，后者证明是否已报过），两道都要做([weaver.com.cn](https://www.weaver.com.cn/subpage/aboutus/news/news-detail.html?id=29576))。
- 金蝶总账里也有一条同源校验：「银行存款科目分录的结算方式和结算号重复则不保存」([help.open.kingdee.com](https://help.open.kingdee.com/dokuwiki_std/doku.php?id=%E5%87%AD%E8%AF%81%E5%BD%95%E5%85%A5))。
- **对关联建模的直接要求**：一旦允许「一张发票被关联到多个报销单」（合单/拆单现实存在），**关联表本身就会成为重复计入的通道**。必须给「同类型关系 + 同一目标凭证」的重复关联告警，或强制走带金额的核销（受余额约束）。

### 3.3 风险三：超核销、部分核销、金额不变量

- Sage 把不变量写进接口：「must not exceed the unallocated balance of the source payment」([Sage](https://developer.sage.com/embedded-accounting/apis/embedded-accounting/latest/openapi/groups/transactions/tags/allocations.md))。
- Xero 处理零星差额的方式是：允许 minor adjustment，差额进 Rounding account——**差额必须落到某个专门的账户/条目，不能凭空消失，也不能悄悄改到某张发票金额上**([mdp.co.nz](https://www.mdp.co.nz/resources-and-news/xero-tip-allocation-of-payments/))。
- 易快报的规则给出了「核销会改变实付金额」的语义：报销 > 借款 → 只付差额；报销 ≤ 借款 → 直接冲抵([ekuaibao.com](https://www.ekuaibao.com/help/ekuaibao1/chapter6/section6-2.html))。**因此带金额的核销关系必须能改变输出金额，而无金额的关联绝对不能。**

### 3.4 风险四：审计轨迹不完整

- 至少要记录：**谁、什么时候、建/改/删了哪条关联**。Xero 把这件事做成每个事务页面底部的 `History & Notes` 时间线([afsl.nz](https://www.afsl.nz/xero-tip-of-the-month-accessing-the-history-and-notes-feature))；用友好会计对「凭证上传附件 / 删除 / 修改」在操作日志里留记录，删除附件时还会问「是否同步删除发票」([23001.cn](http://23001.cn/news.asp?id=11446))。
- **中文法规侧的硬要求**（若将来涉及合规）：
  - 《会计档案管理办法》（财政部、国家档案局令第79号）第八条(三)：电子档案管理系统须「**建立了电子会计档案与相关联的其他纸质会计档案的检索关系**」——即法规直接要求"档案之间可检索的关联关系"存在([gov.cn](https://www.gov.cn/gongbao/content/2016/content_5041555.htm))。
  - 同办法第十九条：**保管期满但未结清的债权债务会计凭证、涉及其他未了事项的会计凭证不得销毁**，纸质单独抽出立卷、电子单独转存——**关联状态会影响保留期限**([gov.cn](https://www.gov.cn/gongbao/content/2016/content_5041555.htm))。
  - 第十二条/第二十四条：电子会计档案移交时**须与元数据一并移交**——所以关系数据是"档案的一部分"，不能只存在本地索引里([gov.cn](https://www.gov.cn/gongbao/content/2016/content_5041555.htm))。

### 3.5 风险五：冲销/红冲 ≠ 关联（语义差别必须显式区分）

- **关联（link）**：只表达"这两张有关"，不改变任何金额、不改变归属期间、不改变对账口径。
- **冲销/红冲（reversal/offset）**：是一笔**新的、有金额方向的**业务，会改变余额与报表；中文实务里「红字更正」和「相反分录」都不等价（红字分录 ≠ 直接做相反分录）([CNKI 期刊摘要](https://wap.cnki.net/touch/web/Journal/Article/ZJCS200003008.html))；冲销凭证的摘要需要写明冲销对象（实务问题：「冲销记账凭证的摘要怎么写」）([dongao.com](https://www.dongao.com/cjks/jjfjc/201910111170334.shtml))。
- **金蝶把「冲销」和「联查单据」并列为凭证查询的两个操作**——说明在成熟系统里它们就是两件事([help.open.kingdee.com](https://help.open.kingdee.com/dokuwiki_std/doku.php?id=%E5%87%AD%E8%AF%81%E5%BD%95%E5%85%A5))。金蝶云星空的采购链路也明确写了「入库单推应付单是暂估应付，**发票到了再冲回（单到回冲或月初红冲）**」——即冲回是业务动作，不是链接([club.kdcloud.com](https://club.kdcloud.com/article/886252982046442240?productLineId=0&lang=zh-CN))。
- **结论**：你的关系类型枚举里，「冲销/红冲」这一项应该**带符号金额 + 双向各写一条**（A 冲 B、B 被 A 冲），并且**默认在合计里生效**（因为它是事实），而「说明/佐证」默认不影响任何合计。

### 3.6 风险六：附件"张数"口径

- 中文实务有一条很硬的规矩：**一张原始凭证只对应一张记账凭证的，直接附在后面；一张原始凭证涉及几张记账凭证的，附在一张主要的记账凭证后面，然后在其他记账凭证上注明附有该原始凭证的记账凭证的编号**（或附复印件）；**一张原始凭证所列支出需几个单位共同负担的，开出「原始凭证分割单」**（分割单必须含凭证名称、日期、单位、经办人签章、接受单位、业务内容、数量、单价、金额和费用分摊情况）——财政部《会计基础工作规范》第五十一条([金蝶精斗云](https://www.jdy.com/news/1110045934.html))。
- **张数按"自然张数"算，不按打印纸页数算**：实务问答明确——一页 A4 上打了三笔银行手续费，可以不裁剪直接装订，但**附件张数必须按 3 张填，不能填 1 张**([kuaizhang.com](https://www.kuaizhang.com/ask/question_10558164.html))；装订规范要求过宽过长附件折叠、过窄过短附件粘贴于凭证粘贴纸，并**在粘贴单空白处分别写出每一类原始凭证的张数、单价与总金额**([dongao.com](https://www.dongao.com/cjks/jjfjc/201909261161916.shtml))。
- **对你的工具的直接影响**：① 「一张图片」和「一张凭证」不是严格 1:1（一页多笔、一笔多页都存在），需要「自然张数」这一独立字段；② 「原始凭证分割单」是**法定的"虚拟凭证/纯文字说明条目"**，这是方案 F 的合规先例；③ 「附在主要凭证后 + 其他凭证注明编号」就是模型 C + 反向指针的法定版本。

### 3.7 风险七：断链、悬空关联、孤儿附件与删除传播

- 金蝶：悬空关联（下推登记了但目标单没保存）、关联丢失（目标单被删除/反审核后重建）、Excel 导入不带关联关系([club.kdcloud.com](https://club.kdcloud.com/article/886252982046442240?productLineId=0&lang=zh-CN))。
- 用友：附件只在源头单据上，下游单据看不到；多个上游关联同一个下游时，表头显示不全([chanjet.com](https://www.chanjet.com/sem/wchatask/qa-73477.html))。
- QBO：删除事务前必须先解除关联（硬约束）([developer.intuit.com](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/invoice))。
- 用友好会计：删除作废凭证或删除凭证附件时，**提示是否同步删除对应发票**——即删除传播必须由用户显式选择([23001.cn](http://23001.cn/news.asp?id=11446))。
- 应对原则：**关联默认"软删除 + 状态 + 时间戳"**；被引用对象不可静默删除；表头（列表）上要能显示"N 个来源中的全部"，或至少给「+N」提示并允许展开——这是用友明确踩过的显示坑。

### 3.8 可以固化为工具规则的 8 条处理原则

1. **分别列示原则**：关联不改变合计口径；只有显式的「冲销/核销」类型才影响金额（IAS 1.32）。
2. **有金额必校验余额**：任何带金额的核销，其分配合计不得超过源凭证金额（Sage 不变量）。
3. **差额要有落点**：不齐平的核销差额必须落到显式的"差额/舍入"条目，不能改写原凭证金额（Xero Rounding account）。
4. **唯一性指纹 + 入口查重**：以凭证号/流水号+金额+日期+对方 建指纹，重复关联/重复计入时告警（合思 + 金蝶结算号校验）。
5. **关系类型必须显式**：说明/佐证、付款↔发票、报销↔发票、冲销、借款↔还款…不能用标签或命名约定隐式表达（Mayan 作者的结论）。
6. **可反向检索**：关联必须双向可见、可搜索、可排序（DEVONthink in/out link 计数）。
7. **审计留痕**：建/改/删关联都要有 who/when/what 记录，且随数据一起可导出（Xero History & Notes；会计档案管理办法第八条(三)/第二十四条）。
8. **删除受引用约束**：被引用的凭证不能静默删除；删除时显式询问是否联动（QBO unlink-before-delete；用友同步删除提示）。

## 4. 候选建模方案 A–F

> 说明：下面用「表/字段」描述数据模型，不是代码。

### 方案 A：轻量「关联表」（多对多 + 关系类型）——**推荐作为主结构**

**数据模型**：新增一张关联表 `凭证关系`（自引用多对多）。字段建议：`id`、`from_凭证id`、`to_凭证id`、`关系类型`（枚举：说明/佐证、付款↔发票、报销↔发票、借款↔还款、冲销、重复件…）、`说明文本`（自由文本，必有）、`方向显示名`（可选，覆盖默认的"上游/下游"措辞）、`可选金额`（仅冲销/核销类使用）、`创建时间`、`来源`（手工/AI建议/导入）。查询时双向各查一次（`from=x OR to=x`），展示时按关系类型分组。

**优点**：① 与你现有 1 图 1 凭证的模型完全正交，不需要动主表；② 一个凭证天然可以有多个关系、多种关系类型；③ 实现成本最低（一张表 + 详情页一个区块）；④ 这是 NetSuite（`Transaction_links` 带 `link_type`）、QBO（`LinkedTxn` 带 `TxnType`）、金蝶（`T_BOTP_LINKTABLE`）共同的形态，业界验证充分。

**缺点**：① 关系多了会有"图"的复杂度（循环、传递闭包），简单 UI 里可能显得乱；② 若把金额也塞进来，容易和"合并金额"混淆——所以金额必须默认空且只在特定类型下可填；③ 没有"组"的概念，一组 12 张发票在列表上仍然散落。

**适合**：你的核心痛点（银行回单↔发票、收据↔付款凭证、冲销、借款↔还款、行程单↔发票↔支付截图）。**不适合**：需要"一个标题下看一整包"的场景（那需要 B）。

### 方案 B：「组 / 事项」（一堆凭证归到一个组，组有标题与备注）

**数据模型**：一张 `事项/组` 表（`id`、`标题`、`备注`、`时间范围`、`可选金额口径说明`）+ 一张成员表（`组id`、`凭证id`、`可选角色`如"主凭证/佐证"）。**本质上 B 是 A 的特例**——把「组」也当成一种可被关联的实体（关联表里 to 指向组），或者干脆把「组」实现为一条特殊凭证并复用 A 的关系。

**优点**：① 列表可以"分组折叠"，一眼看到一个事项的全貌；② 打印时天然可以打成一个包（报销单+全部发票）；③ 有标题/备注，能回答"这是什么"——恰好补上 A 没有的"整体语义"。这是 Paperless 的 saved view／随手记的报销项目／金蝶的合并下推共同证明过的价值。

**缺点**：① 组是"平的"，表达不了"哪张是主、哪张是佐证"的层级，也表达不了组间关系（除非再套 A）；② **组的"合计"是派生值，一旦展示成"这个组的金额"就极易被当成事实金额**（随手记就是把报销金额自动取为组内总和）；③ 一张凭证属于多个组时会再次冲突（这其实说明"组"应该可以由关联推导）。

**适合**：报销单+多发票、差旅三件套、一次采购的全套单据。**不适合**：表达"为什么付"这类一对一语义、以及带金额的核销。

### 方案 C：「主凭证 + 子凭证」自引用父子层级（树）

**数据模型**：在凭证主表上加 `父凭证id`（自引用外键），或用独立的从属表（`父id`、`子id`、`角色`、`排序`）。需要额外约束：防环（不允许形成循环）、是否允许多父（报销单→多发票是多子单父，但一张发票也可能同时属于两个报销单——那就已经破了树）、以及父凭证是否必须"有金额"。

**优点**：① 与中文会计的法定心智模型完全一致：**记账凭证是主件、原始凭证是附件**，凭证上标「附件张数」；一张原始凭证涉及多张记账凭证时的法定做法正是"附在一张主要凭证后 + 其他凭证注明编号"（《会计基础工作规范》第五十一条）；② NetSuite 用「Record is Parent + subtab」实现同样的东西，成熟可用；③ 对"报销单→多发票"这种天然层级，展示和打印都最自然；④ 用友 NCC 的「主单联查子单」交互就是它的成熟 UI。

**缺点**：① **一棵树只能有一个父**——而现实是"一张发票既属于这次报销、又属于差旅事项、又被某笔付款核销"，树会逼你二选一（金蝶为解决这个用了"关联表 + 分录级数量"而不是纯父子）；② 树深了会难以呈现和查询，需要防环；③ 与 A 功能重叠，两者并存会造成"同一件事有两种记法"。

**适合**：严格的"主件—附件"场景（一张报销单 / 一张记账凭证带一批原始凭证），并且你愿意接受"一个子只有一个父"。
**不适合**：多关系、多归属的现实（拆单/合单/多事项交叉）——那种情况应该用 A 表达，把"父子"只当成 A 的一个关系类型。

### 方案 D：放宽为「一张凭证多张图片」（不再是 1 图 1 凭证）

**数据模型**：把"图片"从凭证本体下沉为子表（`凭证id`、`图片序号`、`图片路径`、`是否主图`、`页类型`），凭证主表只留业务字段；或者反向保留 1 图 1 凭证，另加一张"多图归属"表。

**优点**：① 直接解决"一份凭证扫了 3 页"、"一张流水单上有 3 笔"的真实物理形态（实务问答里明确：一页三笔可以不裁，但张数按 3 计）；② 打印装订时更贴近纸本；③ 一旦做了，其他方案都会受益（因为"凭证"终于和"图片"解耦）。

**缺点**：① 迁移成本最高——列表缩略图、详情页、打印、导出、OCR 全部要改；② **会混淆两个本来不同的概念**：「一条业务记录」与「一张自然凭证张数」（法规要求按自然张数计，见 3.6）；如果只做"多图"而不引入"张数"，反而更难满足"附单据 N 张"的要求；③ 一页多笔（一张回单 3 笔手续费）用"多图"解决不了——那是"一个图片对多条业务"的反向问题，通常需要"拆分"功能而不是"多图"。

**适合**：确实存在多页一份凭证（合同+附件、多页发票、行程单）。**不适合**：把它当成"关系的替代品"（Papermerge 的合并就是这条路，合并即丢失来源）。
> 折中建议：先做**"主图 + 副图"**（不改主键语义：凭证仍以主图识别，副图可排序），把成本压到最低，等真的痛了再彻底解耦。

### 方案 E：不改模型，只用标签/备注/命名约定（零结构）——现状

**数据模型**：无新表。用现有标签（如 `2026-03车险`）、备注（写对方凭证的编号/文件名）、命名约定（`RK20260301-01`）。

**优点**：① 零成本，立刻能用；② 不引入任何会计口径风险（因为没有任何"关系"语义被系统承认）；③ 对**一次性、短命**的归堆（"这批是这次出差的"）其实相当好用——Paperless 官方正是推荐用标签当"灵活活页夹"，并用 saved view 当"桌上标签活页夹"。

**缺点**：① 无法回答"谁解释谁"——只能回答"同一堆"，Paperless 讨论里用户的自我评价就是「I would not call this 'linking' but grouping」；② 标签会爆（448 个标签的实例）；③ 关系不可反向检索、不可搜索、不可统计；④ 备注里的编号一旦改名/删档就成死链；⑤ 无法做任何一致性校验（金额、重复）。

**适合**：临时归堆、给关系做"前置筛选"。**不适合**：任何需要长期维护、需要审计、需要打印成附页的关系。

### 方案 F：允许「虚拟凭证/纯文字说明条目」作为独立记录再被关联——**性价比极高，建议与 A 同时做**

**数据模型**：凭证表允许一条记录 `图片 = 空`、`类型 = 说明/备忘/口头约定/邮件确认`，其余字段（日期、金额可空、对方、摘要）照常；它和普通凭证一样可以被 A 的关系表引用。

**优点**：① **极低成本**（就是允许 image 为空 + 一个类型标记），却能补上关系网里最常见的缺环——"为什么付"这句话本身没有载体；② 有多个商业/法定先例：QBO 的 `Attachable` 明确支持"standalone note"（Note 可以单独成为一个实体）、中文实务的「**原始凭证分割单**」是法定的纯文字凭证（《会计基础工作规范》第五十一条）、易快报的"申请单"就是那种"没有票据但要被引用"的单据；③ 让"AI 建议的关系"有一个可以被人工确认的落点。

**缺点**：① 会稀释"一张图就是一张凭证"的直觉，列表里要能一眼区分"有图/无图"；② 必须防止它被误计入任何金额合计（默认金额为空且不参与统计）；③ 打印时要能选择"不打印纯说明条目"。

**适合**：口头约定、微信/邮件确认、公司制度说明、"这笔是预付款，发票后补"、红冲原因的说明。**不适合**：代替真实凭证入账（所以要明确它不参与金额口径）。

### 4.7 组合建议（推荐的最小可用模型）

- **主结构：A（关联表，关系类型 + 说明文本，金额默认空）**；
- **同时上线：F（虚拟说明条目）**——让 A 的两端都可以是"没有图的记录"；
- **把 B（组）实现为 A 的一种特殊关系类型**（"同属一个事项"指向一个"事项"实体，而不是另建一套成员表），这样列表分组折叠和打印成包都能做；
- **C 不单独建树**：把"主凭证—子凭证"作为 A 的一个关系类型（`主件/附件`），只在需要时使用，避免多归属冲突；
- **D 先做"主图+副图"**，并把「自然张数」做成独立字段（可手工填，默认按图片数），不急着把 1 图 1 凭证的模型推翻；
- **E 保留但不扩张**：标签继续做"临时归堆"，一旦同一个标签被用来表达关系超过几次，就提示用户改用关联。

## 5. 交互与输出：这类关系通常怎么呈现

### 5.1 列表

好用的做法：
- **默认平铺，但给"有关系的凭证"一个可点的标记**（数量徽章 / 链接图标）。DEVONthink 的做法最完整：有出链的显示 outgoing 图标、有入链的显示 incoming 图标，且**入链/出链数量是可搜索、可智能分组、可排序的字段**([Take Control 电子书 p.165](https://download.devontechnologies.com/download/ebooks/TCoDEVONthink4-1.0.pdf))。
- **按"事项/组"折叠成一行**，行内显示组标题 + N 张凭证 + 合计（合计只作展示，且要注明是"组内合计"而非"事实金额"）。这是 QBO `Invoices and Received Payments` 报表的形态：按客户分组，Payment 加粗，其关联发票列在下面([gentlefrog.com](https://gentlefrog.com/how-to-find-payments-linked-to-invoices-quickbooks-online/))。
- **筛选器**：「只看有关系的」「只看未关联的孤儿」「只看被引用但未核销的」——这是把关系变成生产力的关键，DEVONthink 的 in/out 计数就是为了这个。

是坑的做法：
- **把关联当作层级自动展开成树**（一旦多归属就会重复出现同一个凭证，用户会以为数据重复）；
- **在列表上直接显示"合并金额"**（一旦显示，用户就会当事实用——参考随手记把报销金额自动取为组内总和）；
- **用标签列表示关系**（标签列会爆，且无法区分关系类型）；
- **表头只显示第一个来源**（用友明确踩过：多张生产加工单关联同一张材料出库单时表头不会显示全部来源单据号）——应显示「+N」并允许展开。

### 5.2 详情

好用的做法（这几条几乎被所有系统重复验证）：
- **一个独立的"相关凭证"区块/页签**，而不是把关系混在标签里。Paperless 社区的提案非常具体：编辑页加 `Referenced documents` 页签，列表可删除、显示**标题 + 日期 + 预览按钮**，点名字跳转；列表页加 link 按钮打开同一列表([discussion #2007](https://github.com/paperless-ngx/paperless-ngx/discussions/2007))。NetSuite 用 subtab、用友 NCC 用【联查】列表，形态一致([developer.yonyou.com](https://developer.yonyou.com/cloud/integrationAsset/assetDetail/1737285921237819394))。
- **列表每行带一列"关系说明"自由文本**，原文示例 `Related insurance:`——这是 Paperless 讨论里最一致的诉求，也是回答"为什么付"的地方([discussion #2007](https://github.com/paperless-ngx/paperless-ngx/discussions/2007))。
- **双向可见且用词明确**：不要在同一个区块里混用"applied"这类双向词。NetSuite 社区已经把这件事变成著名难题（Applied To vs Applying Transaction），教训是**两个方向各给一个区块，且标题写人话**（"这张凭证解释了哪些"/"哪些凭证解释了这张"）([plative.com](https://plative.com/insights/blog/the-netsuite-eternal-conflict-applied-to-vs-applying-transaction/))。
- **审批/复核场景要有"点开看关联单据详情"**：易快报的做法是审批人审批时可直接点击查看所关联申请单的详情([ekuaibao.com](https://www.ekuaibao.com/help/ekuaibao1/chapter7/section7-4.html))。
- **审计轨迹**：详情页给一个 History 时间线（谁在何时建/改/删了关联）([afsl.nz](https://www.afsl.nz/xero-tip-of-the-month-accessing-the-history-and-notes-feature)；用友好会计把附件增删改写进操作日志 [23001.cn](http://23001.cn/news.asp?id=11446))。
- **删除时的显式选择**：QBO 要求先 unlink 再 delete；用友删除凭证/附件时弹窗问"是否同步删除对应发票"([developer.intuit.com](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/invoice)、[23001.cn](http://23001.cn/news.asp?id=11446))。

是坑的做法：
- **自动链接当事实**（Mayan Smart Links 的教训：按元数据规则自动匹配，关系一多就必须为每对关系加新的元数据类型，最后爆炸；作者自己承认需要"手工链接"）([mail-archive](https://www.mail-archive.com/mayan-edms@googlegroups.com/msg01517.html))；正确姿势是 DEVONthink 那样：AI/相似度推荐 + 人工确认。
- **靠改名维护链接**：DEVONthink 的同名文档自动 WikiLink "可能选错且无法强制"，只能改手工 Item Link([Take Control 电子书 p.168](https://download.devontechnologies.com/download/ebooks/TCoDEVONthink4-1.0.pdf))；你的工具要么用不可变的内部 ID 建链，要么提供"自动更新链接显示名"并接受误配。

### 5.3 打印 / 导出

- **打印"主件 + 附页"是最贴合会计实务的形态**：主凭证在下、附件（原始凭证）依次附后，主件上标注**附件张数**；中文装订规范要求在附件粘贴单上**分类列出每一类原始凭证的张数、单价与总金额**([dongao.com](https://www.dongao.com/cjks/jjfjc/201909261161916.shtml)、[kuaizhang.com](https://www.kuaizhang.com/ask/question_10558164.html))。这给你一个很实用的输出设计：**主凭证页 + 附件清单页（按关系类型分类小计）+ 附件逐页**。
- **导出时带"关联清单"**：把关系导出成一张独立清单（源凭证 / 关系类型 / 目标凭证 / 说明 / 金额），比在每个凭证记录里内联关联更安全——它是可核对、可审计、可当作"档案检索关系"的中间物（呼应《会计档案管理办法》第八条(三)要求电子档案与关联档案有检索关系）([gov.cn](https://www.gov.cn/gongbao/content/2016/content_5041555.htm))。
- **对外发送的边界要可控**：QBO 的 `IncludeOnSend` 就是为"这张附件要不要随发票一起发出去"设计的([developer.intuit.com](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/attachable))。你的工具在导出/发送时也应该能选择"是否包含佐证材料"。
- **要接受的现实**：**把关联记录打进排版模板，是全行业都在痛的事**——NetSuite 用户想在 Advanced PDF 模版里打印 related records（已核销的 Payment/Credit 列表）时的唯一回答是「我还没见过能做到的办法，我认为做不到」([stackoverflow](https://stackoverflow.com/questions/46306951/in-netsuite-how-do-i-print-related-records-in-advanced-pdf-html-template))。所以：**别指望"自动排版进正文"，用"附页 + 清单"这种结构化的方式**，成本和成功率都更好。
- **打印张数口径**：一页纸三笔不必裁剪，但**附件张数按自然张数填**（填 3 不填 1）——所以你的打印输出至少要能分别回答两个数字：**装订了几页** 与 **附件（自然张）几张**([kuaizhang.com](https://www.kuaizhang.com/ask/question_10558164.html))。用友把这两个数分成「附件数」与「附单据数」两个字段分开显示，是很值得抄的细节([chanjet.net](http://chanjet.net/news.asp?id=20303))。

### 5.4 一句话总结好用 vs 坑

| 好用 | 坑 |
|---|---|
| 详情页独立"相关凭证"区块 + 每行一句关系说明 | 把关系塞进标签/备注（会爆、不可反向查） |
| 双向可见、两个方向各一个区块、标题写人话 | 用 `applied` 这类双向词命名（NetSuite 的百年难题） |
| 出入链计数可搜索可排序 | 关系只做展示、不可筛选 |
| 关系类型显式枚举 + 自由文本说明并存 | 只用命名约定表达关系类型 |
| 主凭证页 + 附件清单页（分类小计）+ 附件逐页 | 指望自动把 related records 排进正文模版 |
| 删除被引用对象前显式询问/禁止静默删除 | 级联静默删除；悬空关联不清理 |
| 审计时间线（who/when/what） | 只存"当前有关系"，不存历史 |
| 带金额的核销受余额约束、差额有落点 | 汇总/合并金额直接展示成事实金额 |

## 给这个工具的推荐排序（按 实现成本 vs 收益）

| 优先级 | 动作 | 实现成本 | 收益 | 为什么是这个顺序 | 前置/注意 |
|---|---|---|---|---|---|
| **1** | **A：加一张「凭证关系」表（多对多 + 关系类型 + 说明文本），详情页加"相关凭证"区块** | 低（一张表 + 一个区块） | 极高 | 直接命中全部痛点；是 QBO/NetSuite/金蝶的共同形态；不动现有主表，可增量上线 | 金额字段默认留空；关系类型先只放 5–6 个；不要用标签代替 |
| **2** | **F：允许"无图凭证"（说明/备忘/分割单）** | 极低（允许 image 为空 + 一个类型） | 高 | 补上关系网里最常缺的一环（"为什么付"没有载体）；有 QBO standalone note 与"原始凭证分割单"双重先例 | 默认金额为空、不参与合计；列表要能区分有图/无图 |
| **3** | **反向可见 + 可筛选**（详情页两个方向；列表支持"有关系的/孤儿/未闭环"过滤） | 低 | 高 | 没有反向可见，关联就是"只能从 A 走到 B"的死数据；DEVONthink 的 in/out 计数证明价值 | 两个方向的标题写人话，别用 applied |
| **4** | **审计与删除约束**（关联增删改留痕；被引用凭证禁止静默删除；删除时显式询问） | 低–中 | 中高 | 决定这个功能能否长期可信；QBO/用友/Xero 都有明确做法；也是合规要求（会计档案管理办法第八条(三)） | 关系用软删除 + 状态 |
| **5** | **金额一致性校验**（唯一性指纹查重 + 带金额核销的余额约束 + 差额落点） | 中 | 中高（在引入"核销/冲销"时才必要） | 一旦允许"带金额的关系"，重复计入的风险立刻出现；Sage 的不变量可以直接照抄 | 建议第一版干脆**不做**带金额的关系，只做纯关系 |
| **6** | **B：组/事项（可在 A 上实现为一种关系类型）** | 中 | 中高 | "一次差旅/一次报销看全貌 + 打印成一个包"很有用；但它可以用 A 推导，所以排在 A 之后 | 组的合计标注为"组内合计"；避免沿用随手记那种自动汇总成事实金额 |
| **7** | **打印/导出：主件 + 附件清单页（分类小计）+ 附件逐页；导出关联清单** | 中 | 中高 | 打印是这类工具的最终用途；中文装订规范已经把输出格式规定得很具体；"附页+清单"能绕开 NetSuite 那种"打不进正文模版"的行业级难题 | 区分"装订页数"与"自然张数" |
| **8** | **D：一张凭证多张图片（先做"主图 + 副图"）** | 中–高 | 中（只在确有多页/一页多笔时） | 物理形态确实存在，但改造成本最高且会影响列表/打印/OCR 全链路 | 先做副图；同时保留可手填的"自然张数"；不要用合并代替关联 |
| **9** | **C：主凭证 + 子凭证树** | 中 | 低–中（与 A 高度重叠） | 中文会计的法定心智模型很贴合，但"一个子只有一个父"会和多归属现实冲突；建议只作为 A 的一个关系类型 | 如做，必须防环、必须允许"多父"或明确拒绝多父 |
| **10** | **E：标签/备注/命名约定** | 零 | 低（保留即可，别扩张） | 现状可用作临时归堆，Paperless 官方也推荐标签当"灵活活页夹"；但它不是关系建模，448 标签是明确的反面案例 | 当同一标签开始被用来表达"关系"时，提示改用关联 |

**一句话建议**：先做 **1 + 2 + 3 + 4**（四件事加起来仍然很小），它们就能覆盖你列出的绝大部分场景；**带金额的核销（5）留到确实需要做"冲销/借款抵扣"时再上**；**6/7 是体验放大器**；**8/9 只有在真实数据里反复出现"多页一份凭证"或"严格主件-附件"时才值得动模型**；**不要靠 10 硬撑**。
