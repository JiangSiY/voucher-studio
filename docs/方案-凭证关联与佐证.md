# 方案调研：一张凭证需要另一张凭证来解释（凭证关联 / 佐证）

> **性质**：**调研与方案（未开发）**。2026-10-16 由用户提出「有的凭证需要另外的凭证去解释」后调研产出；用户要求「先调研给出方案，不开发」。
> **决策后**：本方案定案的部分转入 `docs/开发方案.md` 的阶段计划，未定项进 `docs/开发日志.md` 挂账表。
> **一句话结论**：推荐 **「关联表（P1）→ 打印/导出带佐证（P2）→ 事项组（P3）」** 三步走，**不动「一张图片就是一张凭证」这条硬约束**。

---

## 1. 问题与场景

### 1.1 现状

当前模型是**一张图片 = 一张凭证**（DB 层唯一索引强制，见 `crates/voucher-core/src/db/schema.rs` 头注释「v2 变化（一图一凭证）」）。凭证只有：日期 / 金额 / 对方账户 / 摘要 / 备注 / 标签 + 一张图；**凭证之间没有任何关系**。

### 1.2 为什么现在需要关系

用户数据实况（挂账 #30 的只读扫描结论）：2026-09 基准 102 张里**增值税/定额发票占 0%**，**69% 是转账/支付截图**。也就是说痛点不是"发票太多"，而是：

> **付款截图只说明"钱付出去了"，不说明"为什么付"** —— 解释它的往往是另一张凭证（发票、收据、报销单、借款单、行程单）。

### 1.3 需要覆盖的场景（按出现概率）

| # | 场景 | 关系形态 |
|---|---|---|
| 1 | 付款截图 ↔ 发票 / 收据（"这笔钱付的是什么"）★最常见 | 两两关联 |
| 2 | 一次付款 → 多张发票（合单） | 一对多 |
| 3 | 一张发票 → 多次付款（拆单） | 一对多 |
| 4 | 报销单 → 多张明细凭证 | 一对多 / 组 |
| 5 | 借款单 → 还款凭证 | 两两关联 |
| 6 | 冲销 / 红冲（一张凭证抵消另一张） | 两两关联（有方向） |
| 7 | 差旅：行程单 + 发票 + 支付截图 | 组 |

### 1.4 期望能力（需用户确认）

1. 能把两张（或几张）凭证**建立关系**，并在详情里看到「谁解释谁」；
2. 能按关系**查**（"这张凭证的佐证有哪些"、"哪些凭证还没被解释"）；
3. 打印 / 导出时**可选**把佐证作为附页；
4. 以后能按**事项/组**聚合查看与统计（差旅、某次采购）。

## 2. 现状与硬约束（证据）

### 2.1 Schema 与升级机制

| 事实 | 证据 |
|---|---|
| 版本号 `SCHEMA_VERSION = 4`，只服务"新版自身的未来升级" | `crates/voucher-core/src/db/schema.rs:21` |
| v1→v4 是**清库重建**（不做数据迁移） | `schema.rs:195-204`（`if version < SCHEMA_VERSION` → `DROP_ALL_V3` + `SCHEMA_V4`） |
| **v5–v8 是"幂等只增"模块**：`ocr_layouts` 表、`period_locks`、`dup_decisions`、三条索引——**不动旧库数据** | `schema.rs:205-215`（`SCHEMA_LAYOUT` / `SCHEMA_V6` / `SCHEMA_V7` / `SCHEMA_V8`） |
| 现有 11 张表：`vouchers` `attachments` `enhance_hits` `export_batches` `export_items` `snapshots` `ocr_cache` `config` `ocr_layouts` `period_locks` `dup_decisions` | `schema.rs:25-170` |
| **测试锁住了表清单**：`schema_creates_eight_tables`（名字已过期，实际 11 张） | `crates/voucher-core/tests/voucher_flow.rs:18-30` |

→ **结论：新增一张关联表按 v5–v8 的模式做就好（`SCHEMA_V9` + `CREATE TABLE IF NOT EXISTS`），旧库无损、无需清库。**

### 2.2 仓库里**已有的两个"关系"先例**（这是本方案可行性的最强证据）

| 先例 | 模型 | 对本次的启示 |
|---|---|---|
| **疑似重复处置** `dup_decisions` | 两两关系表：`a_id` `b_id`（**归一化 a<b**）+ `decision` CHECK + `keep_id/removed_id/removed_payload`（**留痕**）+ `note` + `created_at` + `UNIQUE(a_id,b_id)` | 「两张凭证之间的关系」本仓库**已经做过一次**：pair 表 + 归一化（`dup_decision_repo::normalize_pair`，`dup_review.rs:181/463`）+ 终态 CHECK + 留痕。关联表照抄这套即可 |
| **导出批次** `export_batches` / `export_items` | 组表 + 成员表：`batch_id REFERENCES ... ON DELETE CASCADE` + `voucher_id` + `sort_order` + 索引 | 「事项组」照抄这套即可；**级联删除的语义先例**也在（删批次带走成员） |

其他相关：修改前留痕 `snapshots`（`schema.rs:91`）、封账 `period_locks`（`schema.rs:143`）、对账是**运行时算 + 落 CSV**、**不持久化**（`services/reconcile.rs:67,152`）。

### 2.3 真正的硬约束（不可逾越，均带证据）

1. **「一张图片就是一张凭证」不只一条索引，而是三处同时执行**
   - DB：`CREATE UNIQUE INDEX … idx_attachments_voucher ON attachments(voucher_id)`（`db/schema.rs:60`）
   - 应用层：附加模式前置校验「该凭证已有图片，请使用「更换图片」」（`services/ingestion.rs:84-89`）；批量附加「其余报失败（一图一凭证），仅第一张被导入」（`ingestion.rs:122`）
   - 测试：`attach_mode_rejects_second_image`（`tests/voucher_flow.rs:1123-1149`）、`one_image_creates_one_voucher_each`（`:1057`）
   → 方案 D（一凭证多图）**即使删掉索引也会被应用层校验与既有用例挡住**，且还有第二道闸：内容 MD5 唯一（`services/dedup.rs:29`、`ingestion.rs:361-363`）。
2. **`SCHEMA_VERSION` 不可 bump**：`schema.rs:21` 的 4，配合 `init()` 的 `if version < SCHEMA_VERSION { DROP_ALL_V3 … }`（`schema.rs:196-205`）——**一旦提到 5，所有现存 v4 用户下次启动即清库、凭证全丢**；而且 `tests/voucher_flow.rs:77-78` 硬断言 `user_version == 4`，bump 必红。新表只能走 v5–v8 的「幂等只增」。
3. **表清单测试形同虚设**：`schema_creates_eight_tables`（`tests/voucher_flow.rs:18`）名字过期、且只断言 9 个名字**存在**（`:31-43`，还漏了 `ocr_layouts` / `dup_decisions`）——**新增表不会让它变红**，必须手工同步，否则守卫等于没有。
4. **命令层不得直连 DB**（`scripts/guards.sh:24` 的 `LAYER_PATTERN` + `:34-43`）：关联的建/解/查三项都必须先在 `crates/voucher-core` 落服务函数。
5. **invoke 名两侧必须完全对称**：`src/api/__tests__/invoke-contract.test.ts:57-76` 比对 `client.ts` 的 `invoke("name"` 与 `src-tauri/src/main.rs:254` 的 `generate_handler!`，双向差集为空 → 新命令必须同时改 core 服务 / `main.rs` / `client.ts` 三处。
6. **`export_items` 是导出覆盖度的唯一事实来源**：`dashboard.rs:507-508`（`NOT EXISTS … export_items` 算「从未导出」）、`:517-519`（格式分布）→ 附页若写进 `export_items`，会同时改动「从未导出」台账与格式分布。
7. **删除语义二选一（不存在两全）**：`attachments` / `export_items` / `snapshots` / `ocr_layouts` 都是 `ON DELETE CASCADE`（`schema.rs:44/86/93/131`），而 `dup_decisions` **刻意不加外键**——注释写明「这是审计日志……留痕必须独立于凭证生命周期」（`schema.rs:149-158`）。关联表必须选边：**随删级联**（干净，但"曾经关联过"的记录消失）或**留痕不灭**（独立审计表，但读取端必须容错指向已删凭证的行）。
8. **封账守卫不覆盖关联**：`ensure_dates_open(conn, dates)`（`services/period.rs:41-58`）依赖 `vouchers.voucher_date`，而关联本身没有日期 → 不给新写路径显式查两端日期，关联操作**天然绕过封账**。

9. **关联 ≠ 抵消**（会计口径硬原则）：IAS 1.32「除非准则要求或允许，不得将资产与负债、收益与费用相互抵消」。→ 关联之后**任何合计口径都必须分别列示**：列表、统计、打印、导出都不许出现"关联后合并成一个金额"（本方案 §7 已列为不做项）。
10. **附件张数按「自然张数」，且与「装订页数」是两回事**：一页 A4 打了三笔手续费、不裁剪直接装订，是 **1 页装订、3 张附件**。→ 打印/导出要能分别回答这两个数（中文实务的"附件粘贴单"要求按类列出每类原始凭证的张数、单价与总金额）。
11. **合规要求（《会计档案管理办法》，财政部/国家档案局令第 79 号）**：第八条(三) 电子档案系统须与相关联纸质档案**建立检索关系**；第十九条 **未结清债权债务/未了事项的凭证不得销毁**；第十二/二十四条 电子档案**须与元数据一并移交**。→ 关联关系必须**持久、可检索、可随档案导出**，删除要可追溯（支持 §8-Q3 里"软删/审计表"那一侧，而不是硬删）。
12. **断链是同类系统的头号工程坑**：金蝶「下推后不保存直接关掉 → 悬空关联」「Excel 导入的单据不带关联关系」；用友「附件只挂在申请单上，付款单看不到」「多张上游关联同一张出库单时表头显示不全」。→ 我们的对应要求：删除凭证前必须显式处理关联（或软删）、**导入路径不得产生悬空关联**、列表/表头对多关联要显示「+N」可展开。

## 3. 候选方案对比

| 方案 | 数据模型 | 表达力 | 侵入现有模型 | 打印/导出 | 去重/对账影响 | 成本（本仓库批次） |
|---|---|---|---|---|---|---|
| **A. 关联表**（多对多 + 关系类型） | `voucher_links(a_id,b_id,kind,note,created_at)` | 两两关系、有类型、有方向 | 低（纯新增表 + 右栏区块） | 中（附页需在导出时展开） | 低（与 dup_decisions 并存，需 UI 互斥提示） | **1–2 批** |
| **B. 事项组**（组 + 成员） | `voucher_groups` + `voucher_group_items(sort_order)` | 一对多、可命名、可聚合 | 低–中（新增两张表 + 列表分组视图） | 中（可出封面页） | 低 | **2–3 批** |
| **C. 主从树**（`vouchers.parent_id` 自引用） | 单列自引用（树） | 层级（父→子） | 中（改 vouchers 表 + 所有列表查询要考虑父子） | 中 | **中–高**（列表/计数口径要明确"含子吗"） | 2–3 批 |
| **D. 一凭证多图**（放宽硬约束） | 去掉唯一索引 | 直接多图 | **高**（推翻一图一凭证） | 高（模板重做） | **高**（去重/OCR/编号连锁） | 4+ 批，且违背既定设计 |
| **E. 零结构**（标签/备注约定） | 无 | 只能靠命名约定 | 零 | 无 | 无 | 0（今天就能用） |
| **F. 虚拟凭证**（纯文字说明条目） | vouchers 允许无图 | 可当"说明卡" | 中（列表/打印要处理无图行） | 中 | 低 | 1–2 批 |

**关键判断**（已并入外部实践调研，见 §9 与 [`docs/调研-凭证关系-外部实践.md`](调研-凭证关系-外部实践.md)）：

- **D 不推荐**：一图一凭证有三道闸（§2.3-1），推翻它会连锁改 OCR/去重/编号/模板。若将来真出现"一页多笔/多页一张"的需求，外部实践建议先做**「主图 + 副图」**并保留可手填的**自然张数**（见 §2.3-10），而不是直接改模型。
- **B（组）应做成 A 的一种关系类型**，不并列成第三套结构：这样"组"只是 `kind` 的一个取值，不会额外长出"组的合计"这种派生金额——**随手记把「报销项目」与「金额自动汇总」直接绑定，正是要避免的设计**。
- **C（父子树）不单独建**：一个子只能有一个父，而现实是多归属（同一张发票可能同时属于某次报销、某个事项、某次核销）。只在 A 里保留「有向关系」这一个 kind。
- **E（标签/备注约定）保留但不扩张**：Paperless-ngx 的关联需求帖里有人用 **448 个标签** 只为了把同一批单据粘在一起——明确的反例。
- **F（无图凭证/纯文字说明条目）从"可延后"升级为"建议与 P1 同批做"**：三重先例——QuickBooks 的 standalone `Note`（可脱离事务独立存在）、中文实务**法定的「原始凭证分割单」**、易快报的「申请单」。成本极低，而且正好补上"这笔钱为什么付"缺一个载体的问题（现有 `create_voucher` 并不强制附件，schema 也允许 0 附件——只是导入路径刻意不留空卡，见 §4 P1′）。
- **带金额的关联（核销/冲销）第一版不做**：Sage 的 `Allocations` 带 `Amount` 且强制"不得超过源付款未分配余额"，而 QuickBooks 的 `LinkedTxn` 只有 `{TxnId, TxnType}` 不带金额——**两类必须分开建模**，先做纯语义关系（说明/佐证）。

## 4. 推荐方案（三步走）

### P1 · 关联表（最小可用，1–2 批）

- **表**（`SCHEMA_V9`，幂等只增）：
  ```sql
  CREATE TABLE IF NOT EXISTS voucher_links (
      id         INTEGER PRIMARY KEY AUTOINCREMENT,
      a_id       INTEGER NOT NULL REFERENCES vouchers(id) ON DELETE CASCADE,
      b_id       INTEGER NOT NULL REFERENCES vouchers(id) ON DELETE CASCADE,
      kind       TEXT    NOT NULL CHECK (kind IN ('explains','payment_invoice','reimbursement','offset')),
      note       TEXT    NOT NULL DEFAULT '',
      created_at TEXT    NOT NULL
  );
  CREATE UNIQUE INDEX IF NOT EXISTS idx_voucher_links_pair ON voucher_links(a_id, b_id, kind);
  CREATE INDEX IF NOT EXISTS idx_voucher_links_a ON voucher_links(a_id);
  CREATE INDEX IF NOT EXISTS idx_voucher_links_b ON voucher_links(b_id);
  ```
  - **对称关系**（`explains` / `payment_invoice` / `reimbursement`）写库前**归一化 a<b**（照抄 `dup_decision_repo::normalize_pair`），避免同一对存两条；
  - **有向关系**（`offset` 冲销）保留方向，UNIQUE 用 `(a_id,b_id,kind)` 即可；
  - 删除凭证 → `ON DELETE CASCADE` 自动清理关联（先例：`export_items.voucher_id`）。
- **删除语义（必须选边，见 §2.3-7）**：推荐 **`voucher_links` 加 `ON DELETE CASCADE`**（关联是可撤的元数据，删凭证不留孤儿）
  **＋ 另设 append-only 的 `voucher_link_events(link_id, a_id, b_id, kind, action('linked'|'unlinked'), at)` 且刻意不加外键**（照抄 `dup_decisions` 的理由：留痕必须独立于凭证生命周期）。
  这样"干净"与"留痕不灭"两者兼得，代价是多一张只写不读的小表。
- **服务层**：`link_vouchers` / `unlink_vouchers` / `links_of(voucher_id)`；全部走 `with_tx`（`db/unit_of_work.rs:93-100`，护栏：闭包内不得再取连接）；
  **写路径模板**直接照抄 `voucher_mgr::delete_vouchers_in_tx`（`:157-184`，"同一事务里先写留痕再变更"）。
- **升级安全用例**：照抄 `tests/dup_decisions_upgrade.rs:52-83` 的范式（先 `DROP TABLE voucher_links` 还原老库形态 → 重新 `init()` → 断言凭证数不变 + 新表与索引补齐）。
- **封账（要么显式拦、要么明说不管）**：`ensure_dates_open`（`services/period.rs:41-58`）不会自动生效；建议 P1 **不拦**（关联不改金额/日期，且可解除），但在文档与 UI 提示里写明——若要拦，就得查两端 `voucher_date` 再调该守卫。
- **命令层**：三个薄命令（遵守 `guards.sh layering`：命令层不碰 db）。
- **前端**：右栏 `.inspector` 内、`VoucherEditor` 之后新增「**相关凭证**」区块：搜索/选择凭证（复用现有搜索接口）→ 选类型 → 写备注；双向显示（A 看到 B，B 也看到 A）；行内可「查看」（跳到那一张）与「解除」。
- **列表**：行内加一个"已关联/被解释"的小徽标；可加 `VoucherQuery.hasLinks`（可选，P1 不必须）。

### P1′ · 同批建议：允许「无图凭证」（说明 / 备忘 / 分割单）

**为什么值得同批做**（外部实践三重先例）：QuickBooks 的 `Note` 可脱离事务独立存在；中文实务有**法定的「原始凭证分割单」**（一张原始凭证涉及多张记账凭证时使用）；易快报用「申请单」当被关联对象。它补的正是"付款截图解释不了自己"时缺的那个**载体**。

- **现状已允许**：`create_voucher`（`services/voucher_mgr.rs:24`）不要求附件；`attachments.voucher_id` 的**唯一索引只管上限**（0 或 1 张，`db/schema.rs:60`）。
- **必须与"空卡缺陷"区分**：导入路径刻意不留空卡（`services/ingestion.rs:4,205`；用例 `g3_3_duplicate_reimport_creates_no_empty_voucher`，`tests/voucher_flow.rs:1086-1119`）→ 说明条目要走**单独的显式创建入口**（并有可识别的标记，如 `kind='memo'` 之类），列表与打印要能识别它；**导入路径的"无空卡"保证不能松**。
- **约束**：金额默认空、**不参与任何合计**；不参与"未填金额"之类的待办口径（或单独统计）；列表缩略图用占位；打印时作为"说明页"而不是图片页。
- **成本**：极低（不改主表结构；主要是创建入口 + 列表占位 + 打印分支 + 一组用例），因此建议与 P1 同批。

### P2 · 打印/导出带佐证（1 批）

- 导出对话框加开关「**把相关凭证作为附页**」（默认关）；开关走 `ExportOptions`（`services/export.rs:51-62` + `client.ts:460-465`）。
- **附页绝不能落进 `export_items`**（`services/export.rs:401-414` 的 `voucher_count = items.len()` 会虚增、`dashboard.rs:507-508` 的"从未导出"会把附页凭证误算成已导出）→ 附页只在 **PDF 渲染层**展开：
  - `PdfInput{cards, images}`（`services/pdf.rs:53-56`）是**平铺**结构、没有主从概念 → 需要一个"附页段"约定（如 `images` 每项加 `ownerVoucherId` + `isAppendix`，或在 `PdfInput` 新增 `appendices: Vec<PdfAppendix>`）；
  - **页脚总页数由卡片/图片数现算**（`pdf.rs:120-122`、`:151`、`:366-368`）→ 加附页会自动改变总页数，需在实现时确认这是期望行为（建议：是）；
  - **表格导出（xlsx/csv）不承载附页**——`export_vouchers_table`（`export.rs:183-224`）只写字段与不涉及图片，开关对这两条路径不生效（UI 上要禁用或提示）。
- 批次侧只加一个提示性计数（如 `export_batches.attach_links INTEGER DEFAULT 0`，需走 `schema.rs:214-231` 的"探列再 ALTER"写法）。
- **打印形态（外部实践推荐的"绕开行业难题"做法）**：`主凭证页 + 附件清单页（按关系类型分类小计：类别人数/张数/金额）+ 附件逐页`。
  NetSuite 想把这些直接排进正文模版得到的是"做不到"（行业公认难题），我们不硬碰这条，改出**独立的清单页**。
- **导出「关联清单」**：列出（源凭证 / 关系类型 / 目标凭证 / 说明文本 / 金额-可空），呼应《会计档案管理办法》第八条(三)的"检索关系"，也让 Excel 侧能核。
- **两套张数**：分别给出「装订了几页」与「附件自然张几张」（§2.3-10），不要用一个数字糊过去。
- **对外发送**：勾选是否含佐证（对应 QuickBooks `Attachable.IncludeOnSend` 的思路）。
- 验收：批次张数与「从未导出」口径**不变** + 附页顺序稳定（按 `sort_order`/关联建立时间） + 同一批重复导出结果一致 + 清单页小计与关联数据一致。

### P3 · 事项组（2–3 批）

- `voucher_groups(id,title,note,created_at)` + `voucher_group_items(group_id,voucher_id,sort_order)`（照抄 `export_batches`/`export_items`）；
- 列表支持「按组折叠 / 只看某组」；洞察可按组聚合；打印可选出封面页；
- 到这一步，"合单/拆单/报销单/差旅"都能用组表达，P1 的两两关联仍然保留给"平级互释"。

## 6. 验收标准（可测）

1. 旧库（当前 11 张表的真实库）启动后新表存在、**原有凭证与附件一条不丢**；
2. 建立 A→B 关联后：A 的详情能看到 B，B 的详情也能看到 A（对称类型）；
3. 冲销类型保留方向：A 的详情显示"被 B 冲销"，B 显示"冲销 A"；
4. 同一对同一类型重复建立两次 → 只有一条（归一化 + UNIQUE 生效）；
5. 删除 B → 关联消失、A 打开不报错（CASCADE）；
6. 打印带附页时：页数与关联数一致、批次张数**不含**附页；
7. 关联操作有 `created_at` 记录，可在详情里看到何时建立；
8. 上述每一条都有对应用例（Rust 集成 + 前端契约），且 `bash scripts/guards.sh layering` 仍绿；
9. **升级安全**：老库（v4、无关联表）`DROP TABLE voucher_links` 还原后再 `init()`，凭证/附件行数**不变**且新表与索引补齐（照抄 `tests/dup_decisions_upgrade.rs:52-83`）；
10. **恢复演练**：备份 → 恢复演练后关联关系仍在（补一条 drill 断言；当前零覆盖）；
11. **筛选一致性**（若做「未被佐证」筛选）：列表与「上一张/下一张」的**位置/总数口径一致**（`build_filter_where` 是唯一真源，但 `neighbor` 另拼三条 SQL，`voucher_repo.rs:500-526` 需同步）；
12. `invoke-contract` / `registrationContract` / `deadCodeContract` / `terminologyContract` 仍绿；
13. **无悬空关联**：删除凭证（或关联对象）后，`voucher_links` 与 `voucher_link_events` 里没有指向不存在凭证的活跃行（升级/导入路径同样不得产生）；
14. **多关联可展开**：同一张凭证被 N 张关联时，列表/详情表头显示「+N」并可展开（用友踩过的坑）；
15. **双向可筛选**：详情页两个方向都可见，列表支持"有关系的 / 孤儿（未被佐证）"筛选，且**出入链计数可排序**（DEVONthink 的做法）；
16. **合计不变**：任何筛选/打印/导出路径下，关联都不改变金额合计（关联≠抵消，§2.3-9）。

## 8. 待你决策的问题

1. **关系类型先做哪几种？** 建议 P1 只做三种：`explains`（说明/佐证）、`payment_invoice`（付款↔票据）、`reimbursement`（报销关系）；冲销 `offset` 留到 P2（它牵涉金额语义）。
2. **打印默认带不带佐证？** 建议默认**不带**，在导出时勾选（避免"印出来一堆别人看不懂的附页"）。
3. **删除与留痕怎么选**（本方案唯一「不存在两全」的决策，见 §2.3-7）：推荐 **`voucher_links` 带 CASCADE（干净）＋ 另建 append-only 的 `voucher_link_events`（不加外键，照抄 `dup_decisions` 的审计理由）**，代价是多一张只写不读的小表；替代方案是「关联表不加外键 + 软删 `deleted_at`」，代价是所有读取端都要容错孤儿行。**请选一条。**（外部合规依据倾向后者：《会计档案管理办法》第十九条「未结清债权债务/未了事项凭证不得销毁」+ 第八条(三)要求建立**检索关系**——即"关联过"这件事本身要留存并可检索。）
4. **一对多怎么表达？** 用"多条两两关联"（P1 就能做，够用但啰嗦）还是直接上"组"（P3，需多花 2–3 批）？
5. **哪些凭证算「被解释」？** 是否需要在列表/待处理里加一个「**未被佐证**」的筛选（对应真实痛点：付款截图缺说明）？若要，须同时改 `build_filter_where` + `neighbor` 三条 SQL + `VoucherQuery`（Rust/TS 两侧）。
6. **封账月能不能加/解关联？** 建议**能**（关联不改金额与日期、且可解除），并在 UI 说明「封账保护的是金额与凭证内容」；若要拦，就在写路径里显式查两端 `voucher_date` 调 `ensure_dates_open`。
7. **要不要同批做「无图凭证」（说明/备忘/分割单，§4 P1′）？** 建议**做**——成本极低、有三重先例，且它正是"付款截图缺说明"时最直接的载体。

### 9.1 主流软件怎么建模（结论）

| 系统 | 关系怎么存 | 对我们最有用的一点 |
|---|---|---|
| QuickBooks | 事务对象上的 `LinkedTxn[]`（`{TxnId,TxnType}`，**不带金额**）；附件是独立实体 `Attachable`（`AttachableRef` 指向事务、`IncludeOnSend` 控制随单外发、**Note 可独立存在**） | 「关系」放在**独立结构**里而不是字段拼接；**附件清单可选择性随单发送**；Note 的先例支持 §4 P1′ |
| Xero | **没有通用文档链接**，关系全靠**核销**（`CreditNotes`/`Prepayments`/`Overpayments` + `AmountCredited`）；附件挂在父对象下 | 纯附件挂载解决不了"谁解释谁"；差额必须有落点（Rounding account） |
| Sage | 独立资源 `Allocations{Source,Target,Amount}`，**强制"不得超过源付款未分配余额"** | **带金额的关联必须自带余额不变量** → 与纯语义关系分开建 |
| NetSuite | 行级多对多 `Transaction_links`（复合主键 + `amount_linked`/`link_type_code`），主表另有冗余方向字段 | 行级粒度会让"还原方向"很痛苦；**打印 related records 是行业公认做不到**（SO #46306951） |
| 用友 | 凭证上「**附件数**」与「**附单据数**」**分开显示**，附单据数可下钻 | 张数口径要分两套；"多上游关联同一单据时表头显示不全"是典型坑 |
| 金蝶 | `T_BOTP_LINKTABLE` + 分录级 `...ENTRY`（上查下查依据）；关联在下推时登记 | **悬空关联**（下推未保存即关闭）与 **Excel 导入不带关联**是最常见的断链来源 |
| 费控（易快报/合思/泛微） | 「申请单」字段建链；一个报销单可核销**多笔**借款单；多维唯一性指纹查重 | 核对场景天然是**一对多**；**验真 ≠ 查重**，两道都要 |

### 9.2 文档管理工具

- **Paperless-ngx**：原生无关联，官方把标签定位成 "more versatile folders or binders"——需求帖 #2007 与本项目**同构**（保险理赔↔发票、**付款凭证↔发票**、行程单+酒店+机票），且给出了 UI 提案：编辑页 `Referenced documents` 页签 + 列表 link 按钮 + **每行一列自由文本说明**；反例是 448 个标签。
- **Mayan EDMS**：Smart Links 是"按规则自动引用"，作者在邮件列表里**承认不够用**，说只能靠手工链接。
- **Papermerge**：走"直接合并"（丢来源）。
- **DEVONthink**：Item Links/WikiLinks + 系统维护**入链/出链计数**，且**计数可用于搜索、智能分组与排序** → §6-15 的参考。

### 9.3 会计口径的五条原则（已并入 §2.3 / §7）

1. 关联 ≠ 抵消（IAS 1.32）——合计必须分别列示；
2. 带金额的关联要有余额不变量与差额落点（Sage / Xero）；
3. 重复计入要靠**多维指纹 + 全局台账 + 入口拦截**（合思），且验真与查重是两道；
4. 冲销/红冲 ≠ 关联（红字分录不等于相反分录）——单列，且第一版不做；
5. 附件张数按**自然张数**，与装订页数分开；法定「原始凭证分割单」是纯文字虚拟凭证的先例。

### 9.4 打印与交互（好用 vs 坑）

- **好用**：列表给关系徽章 + 出入链计数可筛选可排序；详情独立「相关凭证」区块，**双向各一块、标题写人话（别用 applied 这种账套术语）**，每行带一句**关系说明文本**；删除时显式询问是否联动；打印走「主凭证页 + **附件清单页（分类小计）** + 附件逐页」。
- **坑**：把关系自动展开成树（多归属会重复出现）；列表直接显示"合并金额"；用标签列表达关系；表头只显示第一个来源；靠改名维护链接。
