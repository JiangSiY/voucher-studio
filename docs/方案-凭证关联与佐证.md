# 方案调研：一张凭证需要另一张凭证来解释（凭证关联 / 佐证）

> **性质**：**调研与方案（未开发）**。2026-10-16 由用户提出「有的凭证需要另外的凭证去解释」后调研产出；用户要求「先调研给出方案，不开发」。
> **决策后**：本方案定案的部分转入 `docs/开发方案.md` 的阶段计划，未定项进 `docs/开发日志.md` 挂账表。
> **一句话结论**：推荐 **「关联表（P1）→ 打印/导出带佐证（P2）→ 事项组（P3）」** 三步走，**不动「一张图片就是一张凭证」这条硬约束**。

---

## 1. 问题与场景

### 1.1 现状

当前模型是**一张图片 = 一张凭证**（DB 层唯一索引强制，见 `crates/voucher-core/src/db/schema.rs` 头注释「v2 变化（一图一凭证）」）。凭证只有：日期 / 金额 / 对方账户 / 摘要 / 备注 / 标签 + 一张图；**凭证之间没有任何关系**。

### 1.2 为什么现在需要关系

用户数据实况（挂账 #30 的只读扫描结论）：2026-09 基准 102 张里**增值税/定额发票占 0%**，**69% 是转账/支付截图**。也就是说痛点不是"发票太多"，而是：

> **付款截图只说明"钱付出去了"，不说明"为什么付"** —— 解释它的往往是另一张凭证（发票、收据、报销单、借款单、行程单）。

### 1.3 需要覆盖的场景（按出现概率）

| # | 场景 | 关系形态 |
|---|---|---|
| 1 | 付款截图 ↔ 发票 / 收据（"这笔钱付的是什么"）★最常见 | 两两关联 |
| 2 | 一次付款 → 多张发票（合单） | 一对多 |
| 3 | 一张发票 → 多次付款（拆单） | 一对多 |
| 4 | 报销单 → 多张明细凭证 | 一对多 / 组 |
| 5 | 借款单 → 还款凭证 | 两两关联 |
| 6 | 冲销 / 红冲（一张凭证抵消另一张） | 两两关联（有方向） |
| 7 | 差旅：行程单 + 发票 + 支付截图 | 组 |

### 1.4 期望能力（需用户确认）

1. 能把两张（或几张）凭证**建立关系**，并在详情里看到「谁解释谁」；
2. 能按关系**查**（"这张凭证的佐证有哪些"、"哪些凭证还没被解释"）；
3. 打印 / 导出时**可选**把佐证作为附页；
4. 以后能按**事项/组**聚合查看与统计（差旅、某次采购）。

## 2. 现状与硬约束（证据）

### 2.1 Schema 与升级机制

| 事实 | 证据 |
|---|---|
| 版本号 `SCHEMA_VERSION = 4`，只服务"新版自身的未来升级" | `crates/voucher-core/src/db/schema.rs:21` |
| v1→v4 是**清库重建**（不做数据迁移） | `schema.rs:195-204`（`if version < SCHEMA_VERSION` → `DROP_ALL_V3` + `SCHEMA_V4`） |
| **v5–v8 是"幂等只增"模块**：`ocr_layouts` 表、`period_locks`、`dup_decisions`、三条索引——**不动旧库数据** | `schema.rs:205-215`（`SCHEMA_LAYOUT` / `SCHEMA_V6` / `SCHEMA_V7` / `SCHEMA_V8`） |
| 现有 11 张表：`vouchers` `attachments` `enhance_hits` `export_batches` `export_items` `snapshots` `ocr_cache` `config` `ocr_layouts` `period_locks` `dup_decisions` | `schema.rs:25-170` |
| **测试锁住了表清单**：`schema_creates_eight_tables`（名字已过期，实际 11 张） | `crates/voucher-core/tests/voucher_flow.rs:18-30` |

→ **结论：新增一张关联表按 v5–v8 的模式做就好（`SCHEMA_V9` + `CREATE TABLE IF NOT EXISTS`），旧库无损、无需清库。**

### 2.2 仓库里**已有的两个"关系"先例**（这是本方案可行性的最强证据）

| 先例 | 模型 | 对本次的启示 |
|---|---|---|
| **疑似重复处置** `dup_decisions` | 两两关系表：`a_id` `b_id`（**归一化 a<b**）+ `decision` CHECK + `keep_id/removed_id/removed_payload`（**留痕**）+ `note` + `created_at` + `UNIQUE(a_id,b_id)` | 「两张凭证之间的关系」本仓库**已经做过一次**：pair 表 + 归一化（`dup_decision_repo::normalize_pair`，`dup_review.rs:181/463`）+ 终态 CHECK + 留痕。关联表照抄这套即可 |
| **导出批次** `export_batches` / `export_items` | 组表 + 成员表：`batch_id REFERENCES ... ON DELETE CASCADE` + `voucher_id` + `sort_order` + 索引 | 「事项组」照抄这套即可；**级联删除的语义先例**也在（删批次带走成员） |

其他相关：修改前留痕 `snapshots`（`schema.rs:91`）、封账 `period_locks`（`schema.rs:143`）、对账是**运行时算 + 落 CSV**、**不持久化**（`services/reconcile.rs:67,152`）。

### 2.3 真正的硬约束（不可逾越）

1. **一图一凭证**：`attachments.voucher_id` 唯一索引（`schema.rs` v2 说明）——"一张凭证多张图"必须推翻它，会连锁影响 OCR 逐张、去重（MD5 一图一凭证）、编号规则、打印模板、列表缩略图。
2. **列表/详情契约**：`VoucherQuery`（`src/api/client.ts`）是列表筛选的唯一入口，新增"按关系筛选"要扩展它并保持后端一致。
3. **导出批次口径**：`export_items` 决定"哪些凭证进过哪次导出"，导出覆盖度统计依赖它（`schema.rs:83-89`）——附页不能默默改变这个口径。
4. **表清单测试**：`voucher_flow.rs:18` 必须同步。
5. **备份**：快照走 `VACUUM INTO`，**新表自动进快照**（无需改 manifest）；恢复是把 db 文件整体换回，所以**风险很低**。

### 2.4 前端落点

| 落点 | 证据 |
|---|---|
| 右栏结构：`.inspector` → `.ins-head`（编号 + 翻张 + 展开）→ `VoucherEditor` → `.ins-meta`（最后修改） | `src/pages/LibraryPage.vue:735-779` |
| 「相关凭证」区块最自然的位置：`VoucherEditor` 之后、`.ins-meta` 之前（不改编辑器内部） | 同上 |
| 列表行已有缩略图 + 编号/日期/对方/状态两行结构，可加"关联"小徽标 | `LibraryPage.vue` 列表区 |

## 3. 候选方案对比

| 方案 | 数据模型 | 表达力 | 侵入现有模型 | 打印/导出 | 去重/对账影响 | 成本（本仓库批次） |
|---|---|---|---|---|---|---|
| **A. 关联表**（多对多 + 关系类型） | `voucher_links(a_id,b_id,kind,note,created_at)` | 两两关系、有类型、有方向 | 低（纯新增表 + 右栏区块） | 中（附页需在导出时展开） | 低（与 dup_decisions 并存，需 UI 互斥提示） | **1–2 批** |
| **B. 事项组**（组 + 成员） | `voucher_groups` + `voucher_group_items(sort_order)` | 一对多、可命名、可聚合 | 低–中（新增两张表 + 列表分组视图） | 中（可出封面页） | 低 | **2–3 批** |
| **C. 主从树**（`vouchers.parent_id` 自引用） | 单列自引用（树） | 层级（父→子） | 中（改 vouchers 表 + 所有列表查询要考虑父子） | 中 | **中–高**（列表/计数口径要明确"含子吗"） | 2–3 批 |
| **D. 一凭证多图**（放宽硬约束） | 去掉唯一索引 | 直接多图 | **高**（推翻一图一凭证） | 高（模板重做） | **高**（去重/OCR/编号连锁） | 4+ 批，且违背既定设计 |
| **E. 零结构**（标签/备注约定） | 无 | 只能靠命名约定 | 零 | 无 | 无 | 0（今天就能用） |
| **F. 虚拟凭证**（纯文字说明条目） | vouchers 允许无图 | 可当"说明卡" | 中（列表/打印要处理无图行） | 中 | 低 | 1–2 批 |

**关键判断**：
- **D 不推荐**：一图一凭证是为"导入即建卡 + MD5 去重 + 逐张 OCR"服务的设计决定，推翻它的收益（少建几张卡）远小于连锁成本。
- **C 与 A/B 的差别**：树只能表达"父子"，而场景 1/5/6 是**平级互释**（谁解释谁不定），用树会别扭；且树会让"列表张数/合计"口径立刻变复杂。
- **E 是兜底**：今天就要用的话，可以在备注里写「佐证：<编号>」并打同一个标签——可检索但不结构化，打印不会带附页。
- **F 有价值但可延后**：真正需要的是"关系"，不是"多一种凭证"。

## 4. 推荐方案（三步走）

### P1 · 关联表（最小可用，1–2 批）

- **表**（`SCHEMA_V9`，幂等只增）：
  ```sql
  CREATE TABLE IF NOT EXISTS voucher_links (
      id         INTEGER PRIMARY KEY AUTOINCREMENT,
      a_id       INTEGER NOT NULL REFERENCES vouchers(id) ON DELETE CASCADE,
      b_id       INTEGER NOT NULL REFERENCES vouchers(id) ON DELETE CASCADE,
      kind       TEXT    NOT NULL CHECK (kind IN ('explains','payment_invoice','reimbursement','offset')),
      note       TEXT    NOT NULL DEFAULT '',
      created_at TEXT    NOT NULL
  );
  CREATE UNIQUE INDEX IF NOT EXISTS idx_voucher_links_pair ON voucher_links(a_id, b_id, kind);
  CREATE INDEX IF NOT EXISTS idx_voucher_links_a ON voucher_links(a_id);
  CREATE INDEX IF NOT EXISTS idx_voucher_links_b ON voucher_links(b_id);
  ```
  - **对称关系**（`explains` / `payment_invoice` / `reimbursement`）写库前**归一化 a<b**（照抄 `dup_decision_repo::normalize_pair`），避免同一对存两条；
  - **有向关系**（`offset` 冲销）保留方向，UNIQUE 用 `(a_id,b_id,kind)` 即可；
  - 删除凭证 → `ON DELETE CASCADE` 自动清理关联（先例：`export_items.voucher_id`）。
- **服务层**：`link_vouchers` / `unlink_vouchers` / `links_of(voucher_id)`；全部走 `with_tx`；关联**不改金额/日期**，故不受期间锁限制（待确认，见 §8）。
- **命令层**：三个薄命令（遵守 `guards.sh layering`：命令层不碰 db）。
- **前端**：右栏 `.inspector` 内、`VoucherEditor` 之后新增「**相关凭证**」区块：搜索/选择凭证（复用现有搜索接口）→ 选类型 → 写备注；双向显示（A 看到 B，B 也看到 A）；行内可「查看」（跳到那一张）与「解除」。
- **列表**：行内加一个"已关联/被解释"的小徽标；可加 `VoucherQuery.hasLinks`（可选，P1 不必须）。

### P2 · 打印/导出带佐证（1 批）

- 导出对话框加开关「**把相关凭证作为附页**」（默认关）；
- PDF 生成时按关联展开附页，页眉标注「附页：<主凭证编号> 的佐证」；
- **口径**：`export_items` 仍只记主凭证 → **批次张数与导出覆盖度不变**；附页在批次里记为一个可查的附加字段（例如 `export_batches.attach_links INTEGER DEFAULT 0`，仅作提示）。
- 验收：批次张数不变 + 附页顺序稳定 + 同一批重复导出结果一致。

### P3 · 事项组（2–3 批）

- `voucher_groups(id,title,note,created_at)` + `voucher_group_items(group_id,voucher_id,sort_order)`（照抄 `export_batches`/`export_items`）；
- 列表支持「按组折叠 / 只看某组」；洞察可按组聚合；打印可选出封面页；
- 到这一步，"合单/拆单/报销单/差旅"都能用组表达，P1 的两两关联仍然保留给"平级互释"。

## 5. 影响面与兼容（逐项核对）

| 面 | 影响 | 处置 |
|---|---|---|
| Schema / 升级 | 新增表 | 按 v5–v8 幂等只增；**不清库**；`SCHEMA_VERSION` 不动（仍 4） |

| 对账 | 对账是运行时算 + CSV，**不读关联** | P1 不动；将来可把"已关联"作为匹配的**更强证据**（另立方案） |
| 期间锁 | 关联不改金额与日期 | 建议**不拦**（可撤元数据），但保留操作留痕（待确认） |
| 留痕 / 审计 | 关联本身是元数据 | 删除采用**软删 or tombstone**？（见 §8 问题 3） |
| 打印 / 导出 | 附页是"附加输出" | 明确"批次张数不含附页"；开关默认关 |
| 测试 | `voucher_flow.rs:18` 表清单；清单1 三处用例口径；新增契约测试 | 每批同步（仓库纪律） |
| 前端契约 | 新增 3 个命令 + 右栏区块 | `registrationContract`/`deadCodeContract`/`terminologyContract` 各自适用规则不变 |

## 6. 验收标准（可测）

1. 旧库（当前 11 张表的真实库）启动后新表存在、**原有凭证与附件一条不丢**；
2. 建立 A→B 关联后：A 的详情能看到 B，B 的详情也能看到 A（对称类型）；
3. 冲销类型保留方向：A 的详情显示"被 B 冲销"，B 显示"冲销 A"；
4. 同一对同一类型重复建立两次 → 只有一条（归一化 + UNIQUE 生效）；
5. 删除 B → 关联消失、A 打开不报错（CASCADE）；
6. 打印带附页时：页数与关联数一致、批次张数**不含**附页；
7. 关联操作有 `created_at` 记录，可在详情里看到何时建立；
8. 上述每一条都有对应用例（Rust 集成 + 前端契约），且 `bash scripts/guards.sh layering` 仍绿。

## 7. 明确不做（本轮范围外）

- **不放宽「一图一凭证」**（方案 D）；
- 不做"自动关联"（靠 OCR/金额自动猜关联）——先手动，将来可做"**建议关联**"提示；
- 不做复式记账语义（本项目是整理打印工具，不是账务系统）；
- 不改编号规则、不改去重口径、不改对账口径。

## 8. 待你决策的问题

1. **关系类型先做哪几种？** 建议 P1 只做三种：`explains`（说明/佐证）、`payment_invoice`（付款↔票据）、`reimbursement`（报销关系）；冲销 `offset` 留到 P2（它牵涉金额语义）。
2. **打印默认带不带佐证？** 建议默认**不带**，在导出时勾选（避免"印出来一堆别人看不懂的附页"）。
3. **删除关联要留痕吗？** 建议**软删**（`deleted_at`）或写一条 tombstone，理由：关联是核对结论的一部分，事后要能回答"当时是不是关联过"。
4. **一对多怎么表达？** 用"多条两两关联"（P1 就能做，够用但啰嗦）还是直接上"组"（P3，需多花 2–3 批）？
5. **哪些凭证算"被解释"？** 是否需要在列表/待处理里加一个"**未被佐证**"的筛选（对应你现在的真实痛点：付款截图缺说明）？

### 9.1 会计软件：区分「匹配」与「关联」两种关系

| 做法 | 要点 | 来源 |
|---|---|---|
| **多对多匹配是标准模型** | Oracle Payables 明文：「一张采购订单发运行可匹配多张发票，一张发票也可匹配多次（多张订单/收货）」——即"一次付款/一张单据 ↔ 多张发票"在应付系统里就是**多对多**，不是主从树 | [Oracle Payables 文档](https://docs.oracle.com/cd/B16981_04/current/acrobat/115apug.pdf)（搜索摘要直接引用） |
| **银行流水 ↔ 业务单据的"匹配"** | QuickBooks Online 把这叫 matching（对账/勾对），是"把银行交易与已有单据关联起来"的运行时动作 | [QuickBooks 关联银行交易](https://quickbooks.intuit.com/learn-support/it-global/help-article/matching-rules/associa-le-transazioni-bancarie-online-quickbooks/L6qyw0PvP_ROW_it)（方向性） |
| **附件挂在交易上** | Xero 的 paperwork 体系是"把文件**挂到**某笔交易/单据"（1 交易 N 文件），而不是"文件之间互相关联" | [Xero: Attach a file to a transaction](https://central.xero.com/0/article/Attach-a-file-to-a-transaction)、[Manage your paperwork](https://central.xero.com/0/guide/a5B3m0000002l9bEAA/manage-your-paperwork-in-xero)（方向性） |
| **原始凭证 → 记账凭证的批量录入** | 金蝶一类国产软件强调的是"原始凭证（发票/回单）**批量生成**记账凭证"，即**映射**而非"凭证互释" | [金蝶：三步骤批量完成原始凭证录入](https://www.kingdee.com/article/1523844484297674753.html)（方向性） |
| **归档制度要求** | 电子发票电子化报销入账归档的官方案例，说明"报销单—发票—入账凭证"之间的对应关系是**归档合规**的一部分（不是可选的便利功能） | [国家档案局：电子发票电子化报销入账归档案例](https://www.saac.gov.cn/daj/qydagz/202103/4b1266cca17144dab5b99902e5ec6639/files/cfede0dc505e4b13aa28ae4be8b42692.pdf)（方向性） |

**对本项目的含义**：主流做法里，"**匹配**"（勾对/对账，可撤销、可重算）与"**关联**"（持久的事实关系）是两种东西。本仓库恰好两者都有先例：
对账是**运行时计算 + CSV**（`services/reconcile.rs:67`），疑似重复处置是**持久两两关系 + 留痕**（`dup_decisions`）。
本次要做的「佐证」属于**后者**。

### 9.2 文档管理工具：关联 + 组/bundle 两套并存

| 做法 | 要点 | 来源 |
|---|---|---|
| **文档关联（association）** | BIMcollab 一类工程文档工具提供"文档关联"——给两份文档建立**有类型的关系**并在两侧显示（与本方案 P1 同构） | [BIMcollab: Document associations](https://helpcenter.bimcollab.com/en/articles/351081-document-associations)（方向性） |
| **关联文档 / 相关文档** | 个人与小团队文档工具普遍提供 "related documents"（双向）+ "bundle/collection"（一组）两种粒度 | [cornerstone Issue #359「Document Linking」](https://github.com/steilerDev/cornerstone/issues/359)、Paperless-ngx 的 related documents 一类（方向性） |
| **逐交易挂链接文档** | 桌面记账工具 GnuCash 支持给**单笔交易**挂"文档链接"（外部文件/URL），是按交易挂载而非文件互链 | [GnuCash 邮件列表：Transaction Linked Document](https://lists.gnucash.org/pipermail/gnucash-user/2026-January/119533.html)（方向性） |

**对本项目的含义**：「**两两关联（有类型、双向）** + **组/合集**」两套并存是被反复验证的组合——正是本方案 P1 + P3 的结构；
而"一张凭证挂多张图"（方案 D）在主流工具里对应的是 **Xero/GnuCash 那种"交易挂附件"**模式，本项目既有的"一图一凭证"等价于把附件当成了凭证本身，推翻它等于换模型。

### 9.3 会计口径风险（通行做法，需在实现时落到校验/提示）

1. **关联 ≠ 合并**：建立关联**不得**改变任何金额合计口径（本方案已把"批次张数不含附页"写进 P2 验收）；
2. **重复计入**：同一对凭证若既在"疑似重复"里被判重复、又在"佐证"里被关联，必须给出互斥提示（§5）；
3. **冲销与佐证不能混为一谈**：冲销（红冲）带金额方向与期间语义，通常单列一种关系类型，且不适合像"佐证"那样默认双向；
4. **审计轨迹**：关联的建立/解除要留痕（谁、何时、什么类型）——本仓库已有 `snapshots` 与 `dup_decisions.removed_payload` 两种留痕先例；
5. **归档一致性**：若将来要"归档/入账"叙事（§9.1 最后一行），关联关系本身就是档案的一部分，删除应为软删。
